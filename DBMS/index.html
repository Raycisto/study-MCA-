1.1 Database System Concepts & Three-Schema Architecture

▾

A Database Management System (DBMS) is sophisticated software that acts as the intermediary between the user and the physical data storage. It provides a systematic and organized way to create, retrieve, update, and delete (CRUD) data. Instead of applications directly accessing files on disk (which would be chaotic, redundant, and insecure), the DBMS provides an abstraction layer that hides complexity and enforces rules.

The Three-Schema Architecture (also called the ANSI/SPARC architecture) was proposed to separate the user applications from the physical database. It defines three levels of abstraction:

  • External / View Level: The top-most layer that end users and application programs interact with. Each user group sees a customized virtual view of the database — only the data relevant to them. For example, an HR employee sees employee records, while a finance employee sees salary records, even though both come from the same underlying database.
  • Conceptual / Logical Level: This describes the entire structure of the entire database — all entities, attributes, relationships, constraints, and security. Database administrators work at this level. It hides physical storage details but describes what data is stored.
  • Internal / Physical Level: The lowest level describing how data is physically stored on disk — file organization, indexing, access paths, compression, and encryption. This level is closest to the actual hardware.

Data Independence is the capability to change the schema at one level without having to change the schema at the next higher level:

  • Logical Data Independence: Ability to change the conceptual schema without altering external schemas or application programs.
  • Physical Data Independence: Ability to change the internal schema (storage structures) without altering the conceptual or external schemas.
💡 Exam Tip: Physical data independence is easier to achieve than logical data independence, because changing the logical structure often impacts all external views built on top of it.

1.2 Enhanced Entity-Relationship (EER) Model

▾

The Entity-Relationship (ER) Model is a high-level conceptual data model used to describe the structure of a database in terms of entities, attributes, and relationships. It was proposed by Peter Chen in 1976 and provides a graphical notation that non-technical stakeholders can understand.

The Enhanced ER (EER) Model extends the basic ER model with additional semantic concepts borrowed from object-oriented thinking, particularly useful for complex databases:

Subclass / Superclass

A subclass is a subset of an entity type (superclass) that has distinct attributes or relationships. E.g., EMPLOYEE is a superclass; ENGINEER and MANAGER are subclasses.

Specialization

Top-down process of defining subclasses from a superclass based on distinguishing characteristics. Creates an IS-A hierarchy.

Generalization

Bottom-up process — combining two or more entity types that share common properties into a higher-level (generalized) entity type.

Inheritance

Subclasses inherit all attributes and relationships of the superclass. A subclass can also have its own local attributes.

Category (Union Type)

A single superclass that represents a collection of entities from different entity types. Unlike specialization, a category is a SUBSET of the union of its superclasses.

Aggregation

Treating a relationship set as an entity set — allowing relationships to participate in other relationships. Used when a relationship itself needs to be associated with another entity.

Constraints of Specialization/Generalization:

  • Disjoint (d): An entity can be a member of at most ONE subclass (mutually exclusive). E.g., a car can be either a SEDAN or an SUV, not both.
  • Overlapping (o): An entity can belong to MORE THAN ONE subclass simultaneously. E.g., an employee can be both an ENGINEER and a PROJECT_MANAGER.
  • Total (double line in diagram): Every entity in the superclass MUST belong to at least one subclass.
  • Partial (single line): Some entities may NOT belong to any subclass — they just exist as superclass instances.
📌 Converting EER to Tables: Each subclass that has additional attributes becomes its own table, with the primary key of the superclass as a foreign key. For total disjoint specialization, sometimes we create only the subclass tables (no superclass table).

1.3 Relational Algebra Operations

▾

Relational Algebra is a procedural query language that provides a theoretical foundation for SQL. It operates on relations (tables) and returns a new relation as output. All fundamental SQL operations can be expressed in relational algebra.

Fundamental Operations (Unary):

  • Selection (σ): Selects rows satisfying a predicate. σage>25(Employee) — gives all employees older than 25. Equivalent to SQL WHERE clause.
  • Projection (π): Selects specific columns from a relation. πName, Salary(Employee) — gives only Name and Salary columns. Equivalent to SQL SELECT with specific columns.
  • Rename (ρ): Renames the output relation or its attributes. ρEmp(ID, FullName)(Employee) — renames the relation.

Set Operations (Binary — require union-compatible relations):

  • Union (∪): Returns all tuples from either relation, removing duplicates. A ∪ B.
  • Intersection (∩): Returns only tuples present in both relations. A ∩ B.
  • Set Difference (−): Returns tuples in first relation but not in second. A − B.

Join Operations (Binary):

  • Cartesian Product (×): Combines every tuple from one relation with every tuple from another. A × B has |A| × |B| tuples.
  • Natural Join (⋈): Combines relations on common attributes — automatically joins on columns with the same name.
  • Theta Join (⋈condition): Joins based on an arbitrary condition (e.g., A.salary > B.minsalary).
  • Equi-Join: Special theta join where condition uses equality operator only.
  • Division (÷): Used when the query involves "for all" — e.g., "students who took ALL courses."
📝 Relational algebra is used by the DBMS query optimizer internally to represent and transform query execution plans. Understanding it helps understand how SQL queries are optimized.

1.4 Database Integrity — Types & Constraints

▾

Database Integrity is the assurance of data accuracy, consistency, and reliability throughout its lifecycle. It acts as a set of rules (constraints) that prevent unauthorized changes or invalid data entry. Integrity is different from Security — Security protects against external threats, while Integrity ensures data remains valid and untampered even from within.

Entity Integrity Constraint

Ensures every row in a table is uniquely identified — typically through a Primary Key. The primary key column must NEVER be NULL and must be unique. Example: StudentID cannot be NULL in a Students table. Guarantees every entity (row) can be distinctly referenced.

Referential Integrity Constraint

Maintains consistent relationships between tables. A Foreign Key in one table must match a Primary Key in the referenced table, or be NULL. Prevents "broken relationships" — e.g., an order cannot reference a CustomerID that doesn't exist in the Customers table.

Domain Integrity Constraint

Enforces that all data values in a column fall within an acceptable domain — the set of all legal values. This includes data type constraints (only integers in Age), format restrictions (date format), range constraints (salary > 0), and NOT NULL rules. Example: An "Age" column must contain integers between 0–150, not letters.

User-Defined Integrity

Implements custom business rules or triggers that go beyond the above three standard types. Example: A CHECK constraint ensuring that an employee's joining date is not after their retirement date. These are specific to the business domain requirements.

Key Integrity

A special form of entity integrity — ensures that all candidate keys (unique identifiers) are indeed unique and non-null across all rows in a relation. Candidate keys are columns (or combinations) that could serve as the primary key.

NULL Integrity

Controls where NULL values are permitted. A NOT NULL constraint on a column means that column must always have a value — no row can leave it empty. This prevents unknown/missing data in critical fields.

💡 Exam Tip: Without integrity, systems face corruption due to human errors, bugs, or malicious actions. Example — without referential integrity, a bank could record a transaction for a non-existent account. Without domain integrity, an "Age" column could store "ABC".

1.5 Schema vs Instance & Codd's Rules

▾

Schema is the overall design/structure of a database — it defines the tables, their columns, data types, constraints, and relationships. The schema is relatively stable and changes rarely. Think of it as the blueprint of the database. Example: The schema says "Students table has (RollNo INT, Name VARCHAR(50), CGPA DECIMAL)."

Instance (Database State / Snapshot) is the collection of actual data (content) stored in the database at a particular moment in time. The instance changes frequently as records are inserted, updated, or deleted. Think of it as the current photograph of the database. Example: At 10AM, the Students table has 200 rows — that's the instance at that moment.

📝 Analogy: Schema = the structure of a form (fields like Name, Age, Address). Instance = a filled-out form with actual data. The form's structure rarely changes, but the filled values change constantly.

Codd's 12 Rules — E.F. Codd proposed these rules in 1985 to define what a truly relational DBMS must support. Key rules for exams:

  • Rule 0 (Foundation Rule): A system must qualify as relational, as a database, and as a management system — managing data entirely through its relational capabilities.
  • Rule 1 (Information Rule): All information in the database must be represented in exactly one way — as values in table (relation) columns.
  • Rule 2 (Guaranteed Access Rule): Every data value must be accessible using: table name + primary key + column name. No pointers allowed.
  • Rule 3 (Systematic Treatment of NULL): NULLs must be uniformly treated as "missing/inapplicable information," independent of data type.
  • Rule 4 (Dynamic Online Catalog): The database description (metadata) must be accessible via the same query language used for normal data (SQL on system tables).
  • Rule 5 (Comprehensive Data Sublanguage): Must support at least one language with a well-defined syntax that can handle all: data definition, view definition, data manipulation, authorization, and transaction management.
  • Rule 6 (View Updating Rule): All views that are theoretically updatable must be updatable by the system.
  • Rule 10 (Integrity Independence): Integrity constraints must be definable in the data sublanguage and stored in the catalog — not in application programs.
  • Rule 12 (Non-Subversion Rule): If a low-level record-at-a-time interface exists, it cannot bypass integrity rules defined at the set-level SQL interface.

2.1 Query Processing & Optimization

▾

Query Processing refers to the set of activities involved in extracting data from a database. When you run a SQL query, the DBMS doesn't just directly execute it — it goes through a pipeline: parsing → translation → optimization → evaluation.

Steps in Query Processing:

  1. Parsing and Translation: The SQL query is checked for syntax errors and translated into an internal form — typically a relational algebra expression or a query tree (parse tree).
  2. Optimization: The query optimizer takes the internal form and generates multiple equivalent execution plans. It then estimates the cost of each plan and selects the cheapest one.
  3. Evaluation (Execution): The selected execution plan is executed by the query evaluation engine, which returns the final result.

Measures of Query Cost — the cost of a query plan is typically measured in terms of:

  • Disk I/O (most important): Number of disk block reads and writes. Since disk access is thousands of times slower than memory, this dominates query cost.
  • CPU Cost: Time for processing in memory — sorting, comparisons, hashing.
  • Communication Cost: In distributed databases, cost of transferring data across a network.

Heuristic Optimization (Rule-Based): The optimizer applies algebraic transformation rules to rewrite the query into a more efficient but equivalent form. Common heuristics include:

  • Push selections down: Apply SELECT (σ) operations as early as possible to reduce the size of intermediate relations (filter rows early).
  • Push projections down: Apply PROJECT (π) early to eliminate unnecessary columns.
  • Combine Cartesian product with preceding selection into a JOIN: Instead of doing a cross product first then filtering, do a join directly.
  • Reorder joins: Join smaller relations first to produce smaller intermediate results.
📌 Cost-based optimization uses statistical information (number of rows, data distribution, index availability) stored in the System Catalog to estimate costs and pick the best plan.

2.2 Functional Dependencies & Normalization

▾

A Functional Dependency (FD) X → Y (read: X determines Y) means that for any two tuples in a relation, if they have the same value for X, they must also have the same value for Y. FDs capture business rules and constraints about data.

Types of Functional Dependencies:

  • Full FD: Y is fully functionally dependent on X if removing any attribute from X causes the dependency to no longer hold.
  • Partial FD: Y depends on only PART of a composite primary key X. This is undesirable (violates 2NF).
  • Transitive FD: X → Y and Y → Z, so X → Z transitively. This causes update anomalies (violates 3NF).
  • Multi-Valued Dependency (MVD) X ↠ Y: For each value of X, there is a set of Y values independent of the other attributes. Causes 4NF violations.

Normal Forms — a hierarchy of design quality:

  • 1NF (First Normal Form): All attribute values must be atomic (indivisible) — no repeating groups, no arrays. Every column holds a single value.
  • 2NF (Second Normal Form): Must be in 1NF AND every non-key attribute must be fully functionally dependent on the entire primary key (no partial dependencies). Only relevant when there is a composite primary key.
  • 3NF (Third Normal Form): Must be in 2NF AND there must be no transitive dependencies — non-key attributes must not depend on other non-key attributes. Every non-key attribute must depend directly on the primary key.
  • BCNF (Boyce-Codd Normal Form): A stronger version of 3NF — for every FD X → Y, X must be a superkey. BCNF eliminates all redundancies based on FDs but may not preserve all FDs.
  • 4NF (Fourth Normal Form): Must be in BCNF AND have no multi-valued dependencies (MVDs). Addresses situations where one attribute multi-determines another independently.
  • 5NF (Fifth Normal Form / Project-Join Normal Form): Must be in 4NF AND every join dependency must be implied by the candidate keys. Handles complex decomposition scenarios.
⚠️ Anomalies prevented by normalization: Insertion anomaly (can't add data without related data), Update anomaly (same data in multiple places must be updated everywhere), Deletion anomaly (deleting a record unintentionally removes other information).

Armstrong's Axioms — rules to derive all functional dependencies from a given set F:

  • Reflexivity: If Y ⊆ X, then X → Y
  • Augmentation: If X → Y, then XZ → YZ
  • Transitivity: If X → Y and Y → Z, then X → Z
Normalization Staircase — 1NF → 2NF → 3NF → BCNF → 4NF → 5NF

2.3 Physical Database Design & Database Tuning

▾

Physical Database Design is the process of deciding how the logical database schema will be physically stored on disk. While logical design focuses on what data to store and its relationships, physical design focuses on how to store it efficiently for the expected workloads.

Key Physical Design Decisions:

  • File Organization: Heap files (unordered, good for bulk loading), Sequential/Sorted files (good for range queries), Hash files (great for equality lookups).
  • Indexing: B+ Tree indexes (for range queries and equality), Hash indexes (for equality only), Clustered indexes (data physically sorted by index key), Non-clustered (data not sorted, extra level of indirection).
  • Partitioning: Splitting large tables into smaller partitions — horizontal (by rows) or vertical (by columns) — to improve query performance and manageability.
  • Denormalization: Intentionally introducing some redundancy to reduce expensive joins, accepting some update anomaly risk for read performance gains.

Database Tuning is an ongoing process of monitoring and improving database performance. It includes:

  • Index Tuning: Adding, removing, or modifying indexes based on actual query patterns from the workload.
  • Query Tuning: Rewriting inefficient SQL queries, using hints to guide the optimizer, avoiding SELECT *, using EXPLAIN PLAN to analyze execution.
  • Schema Tuning: Restructuring tables — merging frequently joined tables, splitting rarely accessed columns into a separate table (vertical fragmentation).
  • Parameter Tuning: Adjusting DBMS configuration parameters — buffer pool size, sort area, number of parallel threads.

2.4 FD Equivalence, Canonical Cover & Minimal Cover

▾

FD Equivalence: Two sets of functional dependencies F and G are equivalent (F ≡ G) if they have the same closure: F⁺ = G⁺. This means every FD derivable from F can be derived from G, and vice versa. To check equivalence, you must verify mutual coverage: F covers G (F ⊇ G⁺) AND G covers F (G ⊇ F⁺).

Steps to Determine Equivalence (F ≡ G):

  1. Check if F covers G: For each FD (X → Y) in G, compute X⁺ using F. If Y ⊆ X⁺ for ALL FDs in G, then F covers G.
  2. Check if G covers F: For each FD (X → Y) in F, compute X⁺ using G. If Y ⊆ X⁺ for ALL FDs in F, then G covers F.
  3. If both conditions hold, F ≡ G. Otherwise, they are NOT equivalent.

Canonical Cover (Minimal Cover) Fc: A minimal set of FDs equivalent to F. It removes all redundancy from F. Properties:

  • Every FD in Fc has a single attribute on the right-hand side (singleton RHS)
  • No FD in Fc is redundant (removing it changes the closure)
  • No attribute on the left-hand side of any FD is extraneous (redundant)
  • Fc ≡ F (same closure as F)

Algorithm to Compute Minimal Cover — Step by Step:

  1. Step 1 — Singleton RHS: Split every FD with multiple attributes on the RHS into separate FDs. E.g., A → BC becomes A → B and A → C.
  2. Step 2 — Remove Extraneous LHS Attributes: For each FD XA → B (where X is the remaining LHS after removing A), check if B ∈ X⁺ computed using F. If yes, attribute A is extraneous — replace XA → B with X → B.
  3. Step 3 — Remove Redundant FDs: For each FD f = (X → B) in the current set, compute X⁺ using F − {f}. If B ∈ X⁺, then f is redundant — remove it.
📝 Worked Example: F = {A → BC, CD → E, B → D, E → A}
Step 1 (split RHS): F = {A→B, A→C, CD→E, B→D, E→A}
Step 2 (remove extraneous LHS): Check if C in CD→E is extraneous: compute D⁺ using F = {D} → not containing E. So C is NOT extraneous. Check if D is extraneous: compute C⁺ = {C} → no E. So D is NOT extraneous either. (In this case LHS are already minimal.)
Step 3 (remove redundant FDs): Check each FD — e.g., is A→C redundant? Compute A⁺ without A→C: A→B→D, so A⁺={A,B,D}. C ∉ A⁺, so A→C is NOT redundant.
Final minimal cover: {A→B, A→C, CD→E, B→D, E→A}

2.5 Lossless Join & Dependency Preservation

▾

When we decompose a relation R into smaller relations R1 and R2 (for normalization), we must ensure the decomposition is good. Two crucial properties determine this:

1. Lossless Join (Lossless Decomposition): A decomposition of R into R1 and R2 is lossless if the original relation R can be perfectly reconstructed by joining R1 and R2:

R = R1 ⋈ R2

The join produces no spurious (extra incorrect) tuples. This is the most critical property — without it, we lose or corrupt information.

Test for Lossless Join (Binary Decomposition): The decomposition {R1, R2} of R is lossless-join with respect to F if and only if:

  • (R1 ∩ R2) → (R1 − R2), OR
  • (R1 ∩ R2) → (R2 − R1)

i.e., the common attributes (R1 ∩ R2) must be a superkey of either R1 or R2.

2. Dependency Preservation: A decomposition is dependency-preserving if every FD in F can be verified in at least one of the decomposed relations R1 or R2, without needing to join them back. Formally, the closure of the union of FDs restricted to each Ri must equal F⁺:

(F₁ ∪ F₂ ∪ … ∪ Fₙ)⁺ = F⁺

  • If dependency preservation holds, we can enforce all constraints locally — no expensive joins needed to check constraints.
  • If it does NOT hold, some FDs can only be checked by joining relations — expensive and often impractical.
⚠️ Key Exam Point: BCNF always guarantees lossless join but may NOT preserve all dependencies. 3NF always preserves dependencies AND guarantees lossless join. This is why 3NF is often preferred over BCNF in practice — it offers a good balance between eliminating redundancy and maintaining constraint enforcement.

Multivalued Dependency (MVD) X ↠ Y: In relation R(X, Y, Z), X multidetermines Y if the set of Y values associated with an X value is independent of the Z values. Formally: whenever two tuples agree on X, we can swap their Y values and both resulting tuples must also be in R.

  • Example: In Courses(Course, Teacher, Textbook) — if each teacher teaches a course independently of textbooks used, we have Course ↠ Teacher and Course ↠ Textbook. This creates redundancy even though there's no FD violation.
  • Every FD is an MVD (but not vice versa). MVDs cause 4NF violations.
  • 4NF: A relation is in 4NF if for every non-trivial MVD X ↠ Y, X is a superkey. Decompose to eliminate MVD-based redundancy.

Join Dependency (JD): A relation R satisfies a join dependency ⋈(R1, R2, ..., Rn) if R can be losslessly decomposed into R1, R2, ..., Rn and reconstructed by natural join. Every MVD is a special case of a JD with two components. JDs that are not implied by candidate keys violate 5NF.

  • 5NF (Project-Join Normal Form): A relation is in 5NF if every join dependency in it is implied by the candidate keys. 5NF eliminates all redundancy related to multi-way joins. Rarely achieved in practice — 3NF or 4NF is usually sufficient.

3.1 PL/SQL – Architecture & Basic Elements

▾

PL/SQL (Procedural Language extensions to SQL) is Oracle Corporation's procedural extension to standard SQL. It combines the data manipulation power of SQL with the procedural power of a programming language — bringing constructs like variables, conditions, loops, error handling, and modular code into the database.

Why PL/SQL? Standard SQL is a declarative, non-procedural language — you say what data you want, not how to get it. But real-world applications require procedural logic — loops, decisions, exception handling. PL/SQL fills this gap. Moreover, PL/SQL code executes inside the database server, which dramatically reduces network round trips and improves performance.

PL/SQL Block Structure — every PL/SQL program is composed of blocks:

PL/SQL Block Structure
-- Optional: DECLARE section
DECLARE
   -- Variables, Constants, Cursors, Exceptions declared here
   v_name  VARCHAR2(50);
   v_sal   NUMBER(10,2) := 0;
   c_rate  CONSTANT NUMBER := 0.15;

-- Mandatory: BEGIN section
BEGIN
   -- Executable statements go here
   SELECT ename, sal
   INTO   v_name, v_sal
   FROM   emp
   WHERE  empno = 7839;

   DBMS_OUTPUT.PUT_LINE('Name: ' || v_name);

-- Optional: EXCEPTION section
EXCEPTION
   WHEN NO_DATA_FOUND THEN
      DBMS_OUTPUT.PUT_LINE('No record found!');
   WHEN OTHERS THEN
      DBMS_OUTPUT.PUT_LINE('Error: ' || SQLERRM);

-- Mandatory: END
END;
/  -- The "/" executes the block in Oracle

Key Elements of PL/SQL:

  • Variables: Used to store temporary data. Declared in DECLARE section. Data types match SQL types (NUMBER, VARCHAR2, DATE) plus PL/SQL-specific types like BOOLEAN.
  • %TYPE: Anchors a variable's data type to a table column — if the column type changes, the variable automatically updates. E.g., v_sal emp.sal%TYPE;
  • %ROWTYPE: Declares a record variable with the same structure as an entire table row. E.g., v_emp emp%ROWTYPE;
  • Constants: Declared with the CONSTANT keyword, value cannot be changed after initialization.
  • Control Structures: IF-THEN-ELSIF-ELSE, CASE, LOOP, WHILE LOOP, FOR LOOP.
  • DBMS_OUTPUT.PUT_LINE: Used to print output to the console. You must run SET SERVEROUTPUT ON before seeing output.
⚠️ Always run SET SERVEROUTPUT ON SIZE UNLIMITED; in SQL*Plus or SQL Developer before executing PL/SQL blocks that use DBMS_OUTPUT.

3.2 Cursors – Implicit & Explicit

▾

A Cursor in PL/SQL is a pointer or handle to the context area — the memory work area that Oracle creates for processing SQL statements. When Oracle executes a SQL statement, it allocates a private memory area called the context area to store parsed query information, result set, and current row pointer. A cursor gives the PL/SQL program control over this context area.

Why cursors? A SELECT statement in SQL returns a complete result set at once. But in PL/SQL, you often need to process one row at a time — perform calculations, update based on conditions, print formatted output row by row. Cursors enable row-by-row (row-at-a-time) processing of query results.

Types of Cursors:

  • Implicit Cursor: Automatically created by Oracle for every DML statement (INSERT, UPDATE, DELETE) and single-row SELECT INTO. You don't declare them — Oracle manages them. You can access attributes using SQL%ROWCOUNT, SQL%FOUND, SQL%NOTFOUND, SQL%ISOPEN.
  • Explicit Cursor: Manually declared by the programmer for queries that return multiple rows. You have complete control — you declare it, open it, fetch rows one by one, and close it.

Cursor Attributes:

Attribute Description
%FOUND TRUE if last FETCH returned a row (or DML affected at least one row)
%NOTFOUND TRUE if last FETCH did NOT return a row
%ROWCOUNT Number of rows fetched so far
%ISOPEN TRUE if the cursor is currently open

Explicit Cursor Lifecycle: DECLARE → OPEN → FETCH → CLOSE

  • DECLARE: Define the cursor with a SELECT query (but don't execute it yet).
  • OPEN: Execute the query, retrieve the result set into memory, position the pointer before the first row.
  • FETCH: Retrieve the current row into variables and advance the pointer to next row.
  • CLOSE: Release the cursor's memory resources. Always close cursors when done.
📌 Cursor FOR LOOP is the most elegant and preferred way to use cursors — it automatically handles OPEN, FETCH, and CLOSE, and creates an implicit loop record variable. Less code, fewer errors.

3.3 Triggers

▾

A Trigger is a named PL/SQL block that is stored in the database and automatically fires (executes) in response to a specific event on a table or view. Unlike stored procedures which must be explicitly called, triggers run automatically when certain database events occur — you cannot call a trigger manually.

Why use Triggers?

  • Enforce complex business rules that cannot be expressed as simple constraints
  • Maintain audit trails — automatically log changes to sensitive data
  • Enforce referential integrity beyond standard foreign key constraints
  • Automatically compute derived column values
  • Generate automatic sequence numbers (before sequences/identity columns were standard)
  • Replicate data to another table or system

Trigger Types based on TIMING (WHEN they fire):

  • BEFORE Trigger: Fires BEFORE the triggering DML statement executes. Useful for validation, modifying NEW values before they're written, logging the attempt.
  • AFTER Trigger: Fires AFTER the DML statement executes successfully. Useful for auditing (logging what actually changed), cascading updates to other tables.
  • INSTEAD OF Trigger: Fires IN PLACE OF the triggering statement — primarily used on Views to make them updatable. The original DML is NOT executed; the trigger body executes instead.

Trigger Types based on LEVEL (HOW MANY TIMES they fire):

  • Statement-Level (default): Fires ONCE per triggering SQL statement, regardless of how many rows are affected. E.g., if UPDATE modifies 100 rows, a statement-level trigger fires only once.
  • Row-Level (FOR EACH ROW): Fires once for EVERY row affected by the triggering statement. If UPDATE modifies 100 rows, a row-level trigger fires 100 times. Has access to :OLD and :NEW pseudo-records.

:OLD and :NEW Pseudo-Records (Row-Level only):

  • :OLD: Contains the original values of the row BEFORE the DML operation.
  • :NEW: Contains the new values of the row AFTER the DML operation.
  • For INSERT: :OLD has no meaning (NULL). :NEW contains the values being inserted.
  • For DELETE: :NEW has no meaning (NULL). :OLD contains the values being deleted.
  • For UPDATE: Both :OLD (original) and :NEW (updated) are available.
⚠️ Mutating Table Error (ORA-04091): A row-level trigger cannot query or modify the table that owns the trigger — because the table is in a state of change during trigger execution. This is a common pitfall.

3.4 Stored Procedures & Functions

▾

A Stored Procedure is a named, compiled, and stored PL/SQL program that encapsulates a series of SQL and PL/SQL statements. Once created, it resides in the database and can be called repeatedly from applications, other procedures, or triggers. Procedures may accept input parameters and return results via output parameters but do NOT return a value directly (unlike functions).

Advantages of Stored Procedures:

  • Performance: Procedures are compiled once and stored in compiled form. Subsequent executions reuse the compiled code — faster than recompiling SQL every time.
  • Reduced Network Traffic: Instead of sending multiple SQL statements over the network, the application sends a single EXEC procedure call. The database executes all logic locally.
  • Code Reuse: Write once, call from many places — multiple applications can share the same procedure.
  • Security: Users can be granted permission to EXECUTE a procedure without having direct SELECT/UPDATE/DELETE rights on underlying tables — the procedure acts as a controlled gateway.
  • Maintainability: Business logic is centralized in the database — changing a business rule only requires changing the procedure, not every application.

Parameter Modes:

  • IN (default): Read-only input parameter. The procedure cannot modify it. Value is passed by the caller.
  • OUT: Write-only output parameter. The procedure assigns a value to it. The caller receives the value after the procedure executes.
  • IN OUT: Both readable and writable. Caller passes a value in; procedure may modify it; modified value is returned to caller.

A Function is similar to a procedure but MUST return a single value using the RETURN statement. Functions can be called within SQL expressions (SELECT, WHERE clauses) if they have no side effects — this is a key advantage over procedures.

A Package is a schema object that groups logically related PL/SQL types, variables, constants, cursors, exceptions, procedures, and functions into a single named unit. Packages have a specification (public interface) and a body (implementation). They promote modularity, encapsulation, and performance (first call loads the entire package into memory).

📌 Difference: Procedure = does something (may have side effects, no return value). Function = computes and returns a value. Use functions when you need a value in a SQL expression; use procedures for complex logic with side effects.

3.5 Views, Indexes & Assertions

▾

A View is a virtual table — it doesn't physically store data but represents a saved SELECT query. When you query a view, Oracle executes the underlying SELECT query and presents the result as if it were a table. Views simplify complex queries, restrict data access, provide data independence, and can present data differently to different users.

Types of Views:

  • Simple View: Based on a single table, no group functions, no DISTINCT, no GROUP BY. Can support DML operations (INSERT, UPDATE, DELETE) directly on the view, which propagate to the base table.
  • Complex View: Based on multiple tables (joins), or uses GROUP BY, DISTINCT, aggregate functions, subqueries. Generally NOT updatable through the view.
  • Materialized View: Unlike regular views, a materialized view physically stores the query results. It trades storage space for faster query performance. Must be periodically refreshed when base data changes.
  • Inline View: A subquery in the FROM clause of another SELECT — it acts as a temporary view for that query.

WITH CHECK OPTION: When specified on an updatable view, ensures that any INSERT or UPDATE through the view must satisfy the view's WHERE condition — you cannot insert data that would then become invisible through the view.

An Index is a database structure that improves the speed of data retrieval at the cost of additional storage space and slower write operations. An index is automatically maintained by the DBMS — you create it and Oracle keeps it synchronized with the table.

  • B-Tree Index (default): A balanced tree structure. Excellent for equality and range queries on high-cardinality columns (many unique values). Supports ORDER BY efficiently.
  • Bitmap Index: Stores a bitmap for each distinct value. Extremely efficient for low-cardinality columns (few unique values like gender, status). Excellent for complex AND/OR conditions in data warehouses.
  • Unique Index: Ensures all values in the indexed column(s) are distinct. Automatically created when you define a UNIQUE or PRIMARY KEY constraint.
  • Composite Index: Index on multiple columns. Column order matters — the index is most effective when queries use the leading column(s) in conditions.

An Assertion is a named constraint that can span multiple tables — unlike CHECK constraints which are tied to a single table. An assertion specifies a condition that the database must always satisfy. In theory, the DBMS checks the assertion after every DML statement. (Note: Many databases including Oracle and MySQL don't fully implement assertions.)

4.1 Transaction Management & ACID Properties

▾

A Transaction is a logical unit of work that comprises one or more SQL statements. A transaction must be treated as an indivisible unit — either ALL statements execute successfully and the changes are made permanent, or NONE of the changes take effect (everything is rolled back to the previous consistent state). This all-or-nothing guarantee is fundamental to data integrity.

ACID Properties — the four fundamental properties that guarantee reliability of transactions:

  • Atomicity: The transaction is treated as a single atomic unit. Either ALL operations in the transaction are executed (COMMIT), or NONE are (ROLLBACK). If a system failure occurs midway, all partial changes are undone. Managed by the Transaction Manager using undo logs.
  • Consistency: A transaction must take the database from one consistent state to another consistent state. All data integrity rules (constraints, triggers, cascades) must be satisfied at the end of the transaction. If a transaction violates a constraint, it must be rolled back.
  • Isolation: Concurrent transactions execute as if they were serial (one after another). Intermediate states of a transaction are NOT visible to other concurrent transactions. This prevents dirty reads, non-repeatable reads, and phantom reads. Managed by concurrency control mechanisms (locks, MVCC).
  • Durability: Once a transaction is committed, its changes are permanent and will survive system failures (power outages, crashes). Achieved through write-ahead logging — changes are written to a stable log before being applied to the database.

Transaction States: Active → Partially Committed → Committed / Failed → Aborted → Terminated

Concurrency Problems:

  • Dirty Read: Transaction T2 reads data written by T1 which hasn't committed yet. If T1 rolls back, T2 has read invalid (dirty) data.
  • Non-Repeatable Read: T1 reads a row; T2 updates and commits that row; T1 reads the row again and gets a different value. The data changed during T1's transaction.
  • Phantom Read: T1 executes a query returning N rows. T2 inserts new rows satisfying T1's query and commits. T1 re-executes the same query and gets N+M rows — new "phantom" rows appeared.
  • Lost Update: T1 and T2 both read a value, both compute updates, and both write back. T2's write overwrites T1's write — T1's update is lost.

4.2 Locking, Deadlocks & Recovery

▾

Locking is the most common concurrency control mechanism. Before reading or writing data, a transaction acquires a lock on that data object. Other transactions must wait until the lock is released.

  • Shared Lock (S-Lock / Read Lock): Multiple transactions can simultaneously hold shared locks on the same data — they can all read concurrently, but nobody can write while shared locks are held.
  • Exclusive Lock (X-Lock / Write Lock): Only one transaction can hold an exclusive lock. No other transaction can read or write the locked data. Required for any modification (INSERT, UPDATE, DELETE).
  • Two-Phase Locking (2PL): A protocol ensuring serializability. Phase 1 (Growing Phase): Transaction only acquires locks, never releases any. Phase 2 (Shrinking Phase): Transaction only releases locks, never acquires new ones. The point between the two phases is the "lock point."
  • Multiple Granularity Locking: Locking can be at different granularities — database, table, page, row. Fine granularity (row-level) allows more concurrency but more overhead. Coarse granularity (table-level) has less overhead but more contention. Intention locks (IS, IX, SIX) are used to communicate intent to lock at a finer level.

Deadlock occurs when two or more transactions are waiting for each other to release locks, creating a circular wait condition where no transaction can proceed. Example: T1 holds lock on A and waits for B; T2 holds lock on B and waits for A.

Deadlock Handling Strategies:

  • Prevention: Prevent deadlocks from ever occurring — use timestamp ordering (Wait-Die or Wound-Wait schemes), require all locks be acquired at transaction start, or impose total ordering on resource acquisition.
  • Detection & Recovery: Allow deadlocks to occur; periodically detect them using a wait-for graph (cycle = deadlock); break the deadlock by aborting (rolling back) one transaction (the victim), typically the youngest or the one with fewest locks.
  • Avoidance: Require transactions to declare all resources upfront; use Banker's algorithm to avoid unsafe states (rarely used in DBMS due to impracticality).

Recovery Techniques:

  • Write-Ahead Logging (WAL): Every change is first recorded in a log (UNDO and REDO information) before being written to the database. This guarantees durability and enables recovery.
  • UNDO: Reverts uncommitted changes after a failure — restores the database to the state before the failed transaction.
  • REDO: Reapplies committed changes that weren't written to disk before the crash (they were in the buffer but lost).
  • Checkpointing: Periodically writing all modified buffer pages to disk and recording the checkpoint in the log — reduces recovery time by limiting how far back in the log recovery must scan.
  • Shadow Paging: Maintains two page tables — current and shadow. The shadow is the last consistent state. On commit, the current becomes the new shadow. Simple but inefficient for large databases.

4.3 Database Security

▾

Database Security encompasses all mechanisms and policies used to protect the database from unauthorized access, misuse, disclosure, and modification. Security must be implemented at multiple layers.

Levels of Database Security:

  • Physical Security: Physical access controls to the server hardware — data center security, hardware theft prevention, disaster recovery.
  • Operating System Security: OS-level user accounts, file system permissions, preventing unauthorized login to the server.
  • Network Security: Encrypting data in transit (SSL/TLS), firewalls, VPNs, restricting database port access.
  • Database System Security: Authentication (verifying identity), Authorization (controlling what authenticated users can do), Audit trails (logging who did what).

Access Control:

  • Discretionary Access Control (DAC): Object owners GRANT and REVOKE privileges to other users. SQL GRANT and REVOKE commands implement DAC. Privileges include SELECT, INSERT, UPDATE, DELETE, EXECUTE on specific objects.
  • Mandatory Access Control (MAC): System-enforced access control based on classification labels. Every data object has a security classification (Unclassified, Confidential, Secret, Top Secret). Users have clearance levels. Users can only access data at or below their clearance level.
  • Role-Based Access Control (RBAC): Privileges are assigned to roles (job functions), and users are assigned to roles. Easier to manage — changing a role's privileges automatically affects all users with that role.

SQL Security Commands:

  • GRANT: Gives privileges — GRANT SELECT, INSERT ON Employee TO HR_User;
  • REVOKE: Takes away privileges — REVOKE INSERT ON Employee FROM HR_User;
  • WITH GRANT OPTION: Allows the grantee to further grant the same privilege to others.
⚠️ SQL Injection is one of the most common database security threats — attackers inject malicious SQL code into input fields. Prevention: parameterized queries / prepared statements, stored procedures, input validation, principle of least privilege.

4.4 2PL Variants — Strict, Rigorous, Conservative

▾

Basic Two-Phase Locking (2PL) guarantees conflict serializability but has two problems: (a) it allows cascading rollbacks (if T1 aborts after T2 read T1's dirty data), and (b) deadlocks are still possible. The following variants address these issues:

Basic 2PL

Growing Phase: Transaction acquires locks, releases none.
Shrinking Phase: Transaction releases locks, acquires none.
Problem: Cascading rollbacks possible — if T1 unlocks A and T2 reads A, then T1 aborts, T2 must also abort.
Ensures: Conflict serializability only.

Strict 2PL

A transaction must hold all its exclusive (write) locks until it commits or aborts. Shared locks can be released during the transaction.
Benefit: Prevents cascading rollbacks — no dirty data is ever read by others since X-locks are held until commit.
Ensures: Strict schedules (recoverable, cascadeless) + conflict serializability.
Drawback: Deadlocks still possible.

Rigorous 2PL

A transaction must hold ALL locks (both shared AND exclusive) until it commits or aborts. The strictest variant.
Benefit: Transactions can be serialized in the order they commit. Easier to implement. No cascading rollbacks.
Ensures: Strict schedules + conflict serializability + transactions commit in serializable order.
Drawback: Reduces concurrency most; deadlocks still possible.

Conservative (Static) 2PL

A transaction must acquire ALL locks it will ever need BEFORE it begins execution (pre-claiming all locks at the start).
Benefit: Completely eliminates deadlocks — since a transaction either gets all locks at once or waits until all are available.
Drawback: Transaction must know all data items it needs upfront (often impractical). Reduces concurrency significantly — transactions wait a long time before starting.
Ensures: Deadlock-free schedules.

4.5 Recovery Techniques — Deferred, Immediate, Shadow Paging, Checkpoint

▾

When a system fails (crash, power outage), the database must be restored to a consistent state. Recovery techniques use the transaction log (Write-Ahead Log) to undo or redo changes.

1. Deferred Update (No-Undo / Redo):

  • Database is NOT updated on disk until a transaction commits.
  • All changes are first recorded in the log. Only after commit are they written to the database.
  • On failure: transactions that committed before the failure need REDO (reapply from log to database). Transactions that did NOT commit need NO action — they never wrote to disk anyway.
  • No UNDO needed — dirty pages were never written to disk.
  • Advantage: Simpler recovery (no UNDO). Disadvantage: Transactions can't write large amounts of data (all buffered until commit).

2. Immediate Update (Undo/Redo):

  • Database MAY be updated on disk before a transaction commits (dirty writes to disk allowed).
  • Every change is first written to the log (WAL), then applied to the database buffer (and possibly flushed to disk).
  • On failure: UNDO uncommitted transactions (their changes must be reversed). REDO committed transactions whose changes weren't fully written to disk.
  • Advantage: Better performance — buffer pages written to disk freely. Disadvantage: Both UNDO and REDO needed during recovery (more complex).

3. Checkpointing:

  • Periodically, the system writes all dirty (modified) buffer pages to disk and records a checkpoint record in the log.
  • During recovery, only log records AFTER the last checkpoint need to be processed — dramatically reduces recovery time.
  • Fuzzy Checkpoint: Allows transactions to continue running during checkpointing (no freeze). The system records the start and end of the checkpoint in the log along with the list of active transactions.

4. Shadow Paging:

  • Maintains TWO page tables: the current page table (points to current database state) and the shadow page table (a copy of the last consistent state).
  • During a transaction: all writes go to new disk pages — the shadow page table is never modified.
  • On Commit: The current page table becomes the new shadow page table (atomically). The old shadow is discarded.
  • On Abort/Failure: Simply restore the current page table to the shadow — all changes are instantly discarded.
  • Advantage: Very simple recovery — no UNDO log needed. Disadvantage: Expensive — involves copying page tables. Causes fragmentation of data on disk. Not efficient for large databases. Does not work well with concurrent transactions.

4.6 Deadlock — Wait-Die & Wound-Wait Schemes

▾

Deadlock prevention using timestamps is an elegant approach. Every transaction is assigned a unique timestamp when it begins (older = lower timestamp = higher priority). Two classical timestamp-based prevention schemes:

Wait-Die Scheme (Non-Preemptive)

When Transaction Ti requests a lock held by Tj:

  • If Ti is older than Tj (Ti has smaller timestamp): Ti WAITS — older transactions are patient.
  • If Ti is younger than Tj: Ti DIES (aborts and restarts with the same original timestamp) — younger transactions give up.

Rule: Old waits for young; young dies if it needs old's lock.

Property: A transaction always waits for or is aborted by an older transaction. Older transactions never die.

Wound-Wait Scheme (Preemptive)

When Transaction Ti requests a lock held by Tj:

  • If Ti is older than Tj: Ti WOUNDS Tj — forces Tj to abort (preempts it). Ti takes the lock.
  • If Ti is younger than Tj: Ti WAITS — younger waits for older to finish.

Rule: Old wounds (kills) young; young waits for old.

Property: Young transactions may be aborted (wounded) by older ones. Older transactions never wait.

Detection-Based Approach (Wait-For Graph): Instead of prevention, allow deadlocks to occur. Maintain a Wait-For Graph where nodes are transactions and directed edge Ti → Tj means Ti is waiting for Tj to release a lock. A cycle in the wait-for graph = deadlock. Periodically check for cycles. When detected, abort one transaction (the victim) to break the cycle. Victim selection criteria: choose the transaction with fewest locks, least work done, or youngest timestamp.

5.1 Parallel Databases

▾

A Parallel Database uses multiple processors and disks working simultaneously to execute database operations faster. As data volumes grew exponentially, single-processor systems became bottlenecks. Parallel databases exploit parallelism — executing parts of a query simultaneously across multiple processors.

Why Parallelism? Processing power follows Moore's Law (diminishing returns), but storage requirements and query complexity grow faster. Parallelism allows horizontal scaling (adding more machines) to meet growing demands.

Architectures for Parallel Databases:

  • Shared Memory (Symmetric Multiprocessing / SMP): All processors share a single pool of memory and disk. Very fast communication (through memory bus). Limited scalability — adding more processors causes memory bus contention. Best for tens of processors. Example: Traditional multi-core servers.
  • Shared Disk: Each processor has its own private memory but ALL processors can access ALL disks. Communication happens via disk I/O. Better scalability than shared memory but disk can become a bottleneck. Example: Oracle RAC (Real Application Clusters).
  • Shared Nothing (Massively Parallel Processing / MPP): Each processor has its own private memory AND its own private disks. No sharing of resources. Communication only via high-speed network messages. Most scalable architecture — can scale to thousands of nodes. Example: Google BigQuery, Amazon Redshift, Apache Hive on Hadoop. Drawback: Complex data redistribution for joins and aggregations.
  • Hierarchical / Hybrid: Combines the above — nodes are SMP clusters connected via a shared-nothing network. Best of both worlds. Used in modern cloud data warehouses.

Types of Parallelism:

  • Inter-Query Parallelism: Multiple queries execute simultaneously, each on a separate processor. Improves overall throughput (transactions per second) in OLTP systems.
  • Intra-Query Parallelism: A single query is split and executed on multiple processors simultaneously. Reduces response time for individual complex queries. Two subtypes: Intra-Operator (parallelizing one operator like sort or hash join) and Inter-Operator (pipeline parallelism — different operators of a query run simultaneously on different processors).

5.2 Distributed Databases

▾

A Distributed Database (DDB) is a collection of logically interrelated databases distributed over a computer network. The data is physically stored at different geographic locations (sites/nodes), but users interact with it as if it were a single centralized database — location transparency is a core goal.

Centralized vs. Distributed Databases:

  • Centralized: All data at one location. Simple to manage, enforce consistency. Single point of failure. Performance bottleneck as load grows. Bad for geographically distributed organizations.
  • Distributed: Data spread across multiple sites. Higher availability (failure of one site doesn't bring down the whole system). Better performance (local queries are fast). Data can be near the users who need it most. But: complex concurrency control, harder to maintain consistency (CAP theorem), complex recovery.

Homogeneous vs. Heterogeneous DDBMS:

  • Homogeneous DDBMS: All sites use the same DBMS software and data model. Easier to manage and integrate. All sites appear as a single unified system. Example: Oracle RAC, MySQL Cluster.
  • Heterogeneous DDBMS (Federated Database): Different sites use different DBMS software and/or data models (e.g., one site runs Oracle, another runs PostgreSQL, another runs MongoDB). Much harder to integrate — requires data translation, schema mapping, query reformulation. Often uses a middleware layer (mediator) to unify access.

Data Fragmentation Strategies:

  • Horizontal Fragmentation: Splitting a table's rows across sites based on some predicate. E.g., North India customers at Delhi site, South India customers at Bangalore site. Each fragment contains a subset of rows but all columns.
  • Vertical Fragmentation: Splitting a table's columns across sites. Each fragment contains all rows but only some columns. Primary key is replicated in all fragments to enable reconstruction via join.
  • Mixed Fragmentation: Combination of horizontal and vertical fragmentation. Most complex but most flexible.

Replication: Storing copies of data at multiple sites. Trade-off: better read performance and availability, but complex update propagation — must keep all copies consistent.

Distributed Concurrency Control — Two-Phase Commit (2PC):

The Two-Phase Commit protocol ensures atomicity across multiple distributed sites — either all sites commit or all sites abort a distributed transaction. Coordinator node manages the process:

  • Phase 1 (Voting Phase): Coordinator sends PREPARE message to all participants. Each participant evaluates if it can commit (checks constraints, logs). Responds YES (ready) or NO (abort). If any says NO, coordinator decides ABORT.
  • Phase 2 (Decision Phase): If all said YES, coordinator sends COMMIT. All participants commit and release locks. If any said NO, coordinator sends ABORT — all participants rollback.
⚠️ CAP Theorem: In a distributed system, you can guarantee at most TWO of: Consistency (all nodes see the same data), Availability (every request receives a response), Partition Tolerance (system continues working despite network partitions). Modern NoSQL databases chose A+P over strict Consistency; traditional RDBMS chose C+A but struggle with P.

5.3 Data Fragmentation & Distributed Query Processing

▾

Data Fragmentation is the process of dividing a global relation into smaller pieces (fragments) and distributing them across different sites. Fragmentation is done based on the access patterns of users at each site to minimize data transfer.

Horizontal Fragmentation

Divides a relation by rows (tuples) based on a predicate. Each fragment is a subset of rows that satisfies a specific condition.
Example: EMPLOYEE relation → Site1 gets employees from Delhi (Dept='NORTH'), Site2 gets employees from Mumbai (Dept='SOUTH'). Each fragment has all columns but different rows.
Reconstruction: Original relation = F1 ∪ F2 ∪ ... ∪ Fn (UNION of all fragments)

Vertical Fragmentation

Divides a relation by columns (attributes). Each fragment contains all rows but only selected columns.
Example: EMPLOYEE(EmpID, Name, Salary, Department) → Site1 gets (EmpID, Name, Department), Site2 gets (EmpID, Salary). Primary key (EmpID) is replicated in all fragments.
Reconstruction: Original = F1 ⋈ F2 ⋈ ... ⋈ Fn (NATURAL JOIN on primary key)

Mixed (Hybrid) Fragmentation

Combines horizontal and vertical fragmentation. A relation is first horizontally fragmented, then each fragment is vertically fragmented (or vice versa).
Most flexible but most complex to manage.

Replication

Storing identical copies of data at multiple sites.
Full Replication: Every site has the full database — maximum read performance, maximum update complexity.
Partial Replication: Some relations replicated, some fragmented.
No Replication: Each fragment stored at exactly one site.

Distributed Query Processing — 4 Phases:

  1. Query Decomposition: The global SQL query is analyzed and broken into sub-queries expressed in relational algebra. Normalization and simplification are applied. Output: an algebraic expression on global relations.
  2. Data Localization: Global relations are replaced with their actual fragments at specific sites. The optimizer maps the global query to queries on fragments. Output: a fragment query.
  3. Global Optimization: The query optimizer minimizes the total cost (primarily data transfer cost — moving data across the network is the dominant cost in distributed systems). It decides which site does what processing and how to assemble results. Generates an optimal global query execution plan.
  4. Local Optimization and Execution: Each site optimizes and executes its local sub-query using its own local DBMS optimizer. Results are returned to the coordinator, which assembles the final result.
💡 Key Cost Factor: In distributed query processing, the dominant cost is data transfer over the network (much more expensive than disk I/O in local systems). The optimizer minimizes data movement — choosing to ship smaller intermediate results rather than large base tables.

5.4 Homogeneous vs Heterogeneous DDBMS & Distributed Transactions

▾

Homogeneous DDBMS: All sites use the same DBMS software and the same data model (e.g., all sites run Oracle 21c). The distributed database appears as a single unified system to users. Communication protocols are uniform. Easier to manage, easier to enforce global constraints. Example: Oracle RAC, MySQL Cluster.

Heterogeneous DDBMS: Different sites use different DBMS software and/or different data models. Challenges: schema heterogeneity, data type incompatibilities, different query languages, different transaction management. Requires middleware (mediator/wrapper) for data translation.

  • Federated Database System: A type of heterogeneous DDBMS where each site maintains autonomy (its own local database) while also participating in a global federation. Each site has an export schema (what it shares) and an import schema (what it uses from others). Loosely coupled.
  • Multidatabase System: Another form where sites are completely autonomous — there's no single global schema. Applications must handle the heterogeneity themselves.

Distributed Transaction Management — 2-Phase Commit (2PC):

2PC ensures all sites either commit or all abort a distributed transaction — guaranteeing atomicity across sites. The transaction has a Coordinator (usually the site that initiated the transaction) and multiple Participants (sites involved).

  1. Phase 1 — Voting (Prepare) Phase:
    • Coordinator writes "Prepare T" to its log and sends PREPARE message to all participants.
    • Each participant checks if it can commit (evaluates local constraints, ensures log is flushed).
    • If YES: participant writes "Ready T" to log and sends VOTE-COMMIT to coordinator.
    • If NO: participant writes "Abort T" to log and sends VOTE-ABORT to coordinator.
  2. Phase 2 — Decision (Commit/Abort) Phase:
    • If ALL votes are COMMIT: Coordinator writes "Commit T" and sends COMMIT to all participants.
    • If ANY vote is ABORT: Coordinator writes "Abort T" and sends ABORT to all participants.
    • Participants execute the decision, write to log, send ACK to coordinator.
    • Coordinator writes "Complete T" after receiving all ACKs.
⚠️ Problem with 2PC — Blocking: If the coordinator crashes after Phase 1 but before Phase 2, participants are stuck in an uncertain state (they voted YES but don't know the final decision). They hold all their locks and wait — this is the "blocking problem" of 2PC. 3-Phase Commit (3PC) was proposed to solve this but is complex and rarely used.

JOIN Operations — All Types with Examples
SQL — All JOIN Types
-- Setup for JOIN examples
CREATE TABLE Dept (
    DeptNo   NUMBER PRIMARY KEY,
    DeptName VARCHAR2(20),
    Location VARCHAR2(15)
);
CREATE TABLE Emp (
    EmpNo    NUMBER PRIMARY KEY,
    EmpName  VARCHAR2(20),
    DeptNo   NUMBER REFERENCES Dept(DeptNo),
    Salary   NUMBER(10,2),
    MgrNo    NUMBER
);

-- ► INNER JOIN: Only matching rows from both tables
SELECT E.EmpName, D.DeptName, E.Salary
FROM   Emp E INNER JOIN Dept D
ON     E.DeptNo = D.DeptNo;

-- ► LEFT OUTER JOIN: All rows from Emp, matching rows from Dept (NULL if no match)
SELECT E.EmpName, D.DeptName
FROM   Emp E LEFT OUTER JOIN Dept D
ON     E.DeptNo = D.DeptNo;

-- Oracle old-style LEFT JOIN (using + on the right side)
SELECT E.EmpName, D.DeptName
FROM   Emp E, Dept D
WHERE  E.DeptNo = D.DeptNo(+);

-- ► RIGHT OUTER JOIN: All rows from Dept
SELECT E.EmpName, D.DeptName
FROM   Emp E RIGHT OUTER JOIN Dept D
ON     E.DeptNo = D.DeptNo;

-- ► FULL OUTER JOIN: All rows from both tables
SELECT E.EmpName, D.DeptName
FROM   Emp E FULL OUTER JOIN Dept D
ON     E.DeptNo = D.DeptNo;

-- ► CROSS JOIN (Cartesian Product): Every combination of rows
SELECT E.EmpName, D.DeptName
FROM   Emp E CROSS JOIN Dept D;

-- ► SELF JOIN: Joining a table with itself (Manager-Employee hierarchy)
SELECT E.EmpName AS Employee,
       M.EmpName AS Manager
FROM   Emp E, Emp M
WHERE  E.MgrNo = M.EmpNo;

SQL — Subquery Types
-- Single-Row Subquery: Inner query returns exactly ONE row
-- Find employees earning more than the average salary
SELECT EmpName, Salary
FROM   Emp
WHERE  Salary > (SELECT AVG(Salary) FROM Emp);

-- Find highest earner in each department
SELECT EmpName, Salary, DeptNo
FROM   Emp
WHERE  (DeptNo, Salary) IN (
           SELECT DeptNo, MAX(Salary)
           FROM   Emp
           GROUP BY DeptNo
       );

-- Multi-Row Subquery: IN, ANY, ALL operators
-- Employees in departments located in 'Delhi'
SELECT EmpName
FROM   Emp
WHERE  DeptNo IN (
           SELECT DeptNo
           FROM   Dept
           WHERE  Location = 'Delhi'
       );

-- ANY: salary > at least one salary in dept 10
SELECT EmpName, Salary
FROM   Emp
WHERE  Salary > ANY (SELECT Salary FROM Emp WHERE DeptNo=10);

-- ALL: salary > every salary in dept 10
SELECT EmpName, Salary
FROM   Emp
WHERE  Salary > ALL (SELECT Salary FROM Emp WHERE DeptNo=10);

-- EXISTS: correlated subquery checking existence
SELECT DeptName
FROM   Dept D
WHERE  EXISTS (
           SELECT 1
           FROM   Emp E
           WHERE  E.DeptNo = D.DeptNo  -- correlated: references outer query
       );
-- Lists departments that HAVE at least one employee

-- Correlated Subquery: inner query references outer query column
-- Find employees earning more than average in THEIR OWN department
SELECT EmpName, DeptNo, Salary
FROM   Emp E1
WHERE  Salary > (
           SELECT AVG(Salary)
           FROM   Emp E2
           WHERE  E2.DeptNo = E1.DeptNo  -- references E1 from outer
       );

-- Inline View (Subquery in FROM clause)
SELECT * FROM (
    SELECT EmpName, Salary,
           RANK() OVER (ORDER BY Salary DESC) AS Rnk
    FROM   Emp
) WHERE Rnk <= 3;  -- Top 3 earners

DECLARE
    v_name   Employee.EmpName%TYPE;

PL/SQL — Explicit Cursor (Manual OPEN-FETCH-CLOSE)
DECLARE
    -- Declare the cursor with a SELECT statement
    CURSOR c_emp IS
        SELECT EmpName, Salary, EmpCity
        FROM   Employee
        WHERE  Salary > 5000
        ORDER BY Salary DESC;

    -- Variable to hold fetched row
    v_name  Employee.EmpName%TYPE;
    v_sal   Employee.Salary%TYPE;
    v_city  Employee.EmpCity%TYPE;

BEGIN
    DBMS_OUTPUT.PUT_LINE('=== Employees with Salary > 5000 ===');

    OPEN c_emp;  -- Execute the query; position pointer before first row

    LOOP
        FETCH c_emp INTO v_name, v_sal, v_city;
        EXIT WHEN c_emp%NOTFOUND;  -- Exit when no more rows

        DBMS_OUTPUT.PUT_LINE(
            RPAD(v_name, 15) ||
            RPAD(v_city, 12) ||
            v_sal
        );
    END LOOP;

    DBMS_OUTPUT.PUT_LINE('Total rows: ' || c_emp%ROWCOUNT);

    CLOSE c_emp;  -- Always close! Releases memory
END;
/
PL/SQL — Cursor FOR LOOP (Best Practice)
-- Cursor FOR LOOP: Oracle automatically handles OPEN, FETCH, CLOSE
-- Creates implicit loop record; much cleaner and safer!
DECLARE
    CURSOR c_emp IS
        SELECT EmpName, Salary, EmpCity
        FROM   Employee;
BEGIN
    FOR rec IN c_emp LOOP
        -- rec is implicitly declared; has fields matching cursor columns
        DBMS_OUTPUT.PUT_LINE(
            rec.EmpName || ' | ' ||
            rec.EmpCity || ' | Rs.' ||
            rec.Salary
        );
    END LOOP;
    -- No OPEN or CLOSE needed — Oracle handles automatically
END;

-- First create an audit log table
CREATE TABLE Salary_Audit (
    AuditID     NUMBER PRIMARY KEY,
    EmpCode     NUMBER,

    NewSalary   NUMBER(10,2),

-- AFTER UPDATE trigger to log salary changes
CREATE OR REPLACE TRIGGER trg_salary_audit
AFTER UPDATE OF Salary ON Employee
FOR EACH ROW
WHEN (NEW.Salary != OLD.Salary)  -- Only when salary actually changes
BEGIN
    INSERT INTO Salary_Audit
    VALUES (audit_seq.NEXTVAL,
            :OLD.EmpCode,
            :OLD.Salary,
            :NEW.Salary,
            USER,      -- Current logged-in user
            SYSDATE);
END;

SQL — Transaction Control & Security
-- ══ TRANSACTION CONTROL (TCL) ══

-- COMMIT: Make all changes since last COMMIT permanent
UPDATE Employee SET Salary = 20000 WHERE EmpCode = 1;
COMMIT;  -- Change is now permanent and visible to others

-- ROLLBACK: Undo all changes since last COMMIT
UPDATE Employee SET Salary = 0;  -- Oops! Accidental update
ROLLBACK;                         -- Undo: reverts all salaries

-- SAVEPOINT: Create a partial undo point within a transaction
INSERT INTO Employee VALUES (10, 'Test1', 'Delhi', SYSDATE, SYSDATE, 5000);
SAVEPOINT sp1;  -- Mark this point

INSERT INTO Employee VALUES (11, 'Test2', 'Mumbai', SYSDATE, SYSDATE, 6000);
SAVEPOINT sp2;  -- Another savepoint

INSERT INTO Employee VALUES (12, 'Test3', 'Chennai', SYSDATE, SYSDATE, 7000);

ROLLBACK TO sp1;  -- Only Test1 remains; Test2 and Test3 are undone
COMMIT;           -- Commit Test1 permanently

-- WITH GRANT OPTION allows HR_USER to further grant to others

-- GRANT all DML on a table
GRANT ALL ON Employee TO ADMIN_USER;

-- REVOKE: Take away privileges
REVOKE INSERT ON Employee FROM HR_USER;
REVOKE ALL ON Employee FROM ADMIN_USER;

-- Create and manage ROLES
CREATE ROLE hr_role;
GRANT SELECT, UPDATE ON Employee TO hr_role;
GRANT hr_role TO HR_USER1;  -- User gets all role privileges
GRANT hr_role TO HR_USER2;

-- ══ ISOLATION LEVELS ══
-- Set transaction isolation level
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;    -- Default in Oracle
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;      -- Strictest
SET TRANSACTION READ ONLY;  -- No DML allowed in this transaction
