Introduction to Software Engineering
Software fundamentals, characteristics, SDLC models, and agile methods
What is Software Engineering?
definition▶
IEEE Definition

Software engineering is the application of a systematic, disciplined, quantifiable approach to the development, operation and maintenance of software — i.e., the application of engineering to software.

Pressman's Definition

The establishment and use of sound engineering principles in order to obtain economically software that is reliable and works efficiently on real machines.

Why did SE start?

SE formally began at the 1968 NATO Software Engineering Conference. The trigger was the Software Crisis of the 1960s–70s, where software projects faced:

  • Projects going over budget and missing deadlines
  • Poor software quality and unreliable performance
  • Difficulties in maintenance and updates
  • Mismatch between user requirements and final product
  • Lack of proper documentation and communication
Historical Examples of Software Crisis

Therac-25 (1985–87): Radiation therapy machine with software bugs → patient deaths due to poor testing, no safety interlocks.
Y2K Bug: Systems used 2-digit years; no foresight about scalability and future-proofing.
Windows 95/98/ME: Rushed releases, inadequate regression testing, BSODs.

Software Characteristics
core▶
Key Insight

Software is engineered, not manufactured. It doesn't wear out with age or usage — but it needs updates to adapt to new requirements. It continues to be custom-built.

Characteristic Description Example
Functionality Set of features and capabilities provided to users — includes data storage, processing, UI, security, networking Google Search returning accurate results in <1s
Reliability Ability to perform intended functions correctly and consistently over time; bugs, poor algorithms, inadequate testing cause failures ATM always dispensing correct cash amount
Efficiency Optimal use of resources (memory, CPU, bandwidth); poorly designed algorithms, unoptimized code reduce efficiency WhatsApp working on 2G/3G; Zoom optimizing quality by bandwidth
Usability Extent to which software can be used with ease; time/effort needed to learn it Intuitive UI accessible to both expert and novice users
Maintainability Ease with which modifications can be made to extend functionality, improve performance, or correct errors Modular code where fixing a cart error means touching only the cart module
Portability Ability to transfer software from one environment to another with minimum changes Java's "write once, run anywhere" principle
Software Process
core▶
Definition

A software process is a collection of related activities for producing quality software. It defines the way to produce software — including the life-cycle model, tools, and individuals involved.

Four Core Activities

Activity 1
Software Specification
Defines functions and conditions; uses requirements engineering to produce the specification document
Activity 2
Design & Implementation
Converts requirements into design and implements via programming languages (C, Java, Python, etc.)
Activity 3
Software Validation
Verifies software fulfills client requirements through unit testing, system testing, acceptance testing
Activity 4
Software Evolution
Continuous modification to accommodate changing needs — also called software maintenance

Process Description also includes:

  • Products: Outcomes of process activities (e.g., architectural blueprint)
  • Roles: Responsibilities (project manager, developer, maintenance engineer)
  • Pre- and post-conditions: Conditions maintained during development

Types of Software Process

  • Plan-driven: Requirements are fixed, plans are concrete and not changed (e.g., safety-critical systems)
  • Agile: Process steps are flexible and change per requirement changes (e.g., business software)

Phases of Software Life Cycle

Requirements → Specification (Analysis) → Design → Implementation → Integration → Maintenance → Retirement

Layered Technology (Pressman)

Process → Methods → Tools — all built on a foundation of Quality.

Waterfall Model
exam▶
Origin

Developed in 1970 by Royce. Also called the software life cycle. It is sequential — one phase must complete before the next begins, like a waterfall.

Phases (in order)

  1. Requirement Definition: Gather what the client wants
  2. System & Software Design: Architecture/blueprint of the software
  3. Implementation & Unit Testing: Convert design to programs; test each unit
  4. Integration & System Testing: Combine components, test the complete system
  5. Operation & Maintenance: Deploy, accommodate new requirements
Documents per Phase

Phase 1 → SRS | Phase 2 → HLD + DFDs + ERD | Phase 3 → Source Code + Unit Test Results | Phase 4 → Integration Test Plan + Defect Logs | Phase 5 → User Manual + Maintenance Log

Key Characteristics

  • Sequential — phases don't overlap
  • Each phase starts only after the previous completes
  • Work can be divided among different classes of experts
  • Well-documented at every stage
✅ Advantages ❌ Disadvantages
Simple and easy to understand Rigid — difficult to accommodate mid-project changes
Each phase is well-documented No working software until the very end
Well-suited for smaller systems with stable requirements Not suitable for complex or long-ongoing projects
Progress can be tracked accurately Integration done at the end — bugs found late

Best for:

Government & defence software, medical/aerospace systems, core banking, embedded/hardware-based software — where requirements are clear, fixed, and well-documented.

Relative Effort

Among all phases: Maintenance consumes maximum effort. Among development phases: Testing consumes maximum effort.

Iterative Waterfall & Build-and-Fix Model
core▶
Build-and-Fix Model

The oldest approach (1950s–60s). No requirement analysis, no design phase, no documentation. Programmers start coding immediately and fix issues as they arise. Simple but highly problematic for complex systems.

Iterative Waterfall

The classical waterfall assumes no defect is introduced in any phase — which is unrealistic. In practice, defects are introduced in almost every phase and detected much later.

The iterative waterfall adds feedback paths — when a defect is detected, we go back to the phase where it was introduced and redo work. Documents still reflect a classical waterfall for comprehension.

Incremental Development Model
exam▶
Core Idea

Develop the software in parts (increments). Get user feedback after each increment and incorporate it. Based on agile software development — if there's a mistake, going back is easier than in Waterfall.

Three Repeated Phases

  • Specification: Collect requirements, prepare system specifications
  • Development: Prepare design/model and complete programming
  • Validation: Test the developed software to ensure client requirements are fulfilled

Each repetition produces a new version/increment. Urgent work goes in first; additional features are added based on customer response.

Key Features

  • Software product developed in increments/steps
  • Few functions developed first → working model → more functions added
  • Requirements collected using a fixed method (like Waterfall) but coding, integration, and testing done incrementally
  • Uses a mix of both planned and agile software processes
✅ Advantages ❌ Disadvantages
Users' changes can be incorporated Multiple versions can be costly
Most important functionality developed first with better quality Frequent changes can corrupt structure
Less time; easier error detection and correction Clients must be involved — not always easy
Prototyping Model
exam▶
Definition

A prototype is a starting/initial version of a software system with limited functional capabilities, low reliability, and inefficient performance. It is used to demonstrate concepts, clarify requirements, and get feedback before the final system is built.

Why build a prototype?

  • Illustrate input data formats, messages, reports, and dialogs to the customer
  • Examine technical issues (response time, algorithm efficiency)
  • It's impossible to "get it right" the first time — plan to throw away the first product for a good final product

Prototype Development Process

Requirements Gathering → Quick Design → Build Prototype → Customer Evaluation → Refine Requirements → (repeat) → Customer Satisfied → Design → Implement → Test → Maintain

Types of Prototyping

1. Evolutionary Prototyping

A prototype is developed, given to clients for use, refined based on feedback, and modified in several iterations. Starts with best-understood requirements.

  • Useful when specifications are not fully known (AI/ML, user interface systems)
  • Builds system as a set of increments delivered to customers
  • Advantage: Quick delivery, client involved from the start
  • Drawback: Requires specialist skills; expensive maintenance; management and contractual problems
2. Throw-away (Rapid) Prototyping

A trial version is developed for poorly understood requirements, given for experimentation, then discarded. The actual system is then developed using the Waterfall or another model.

  • Fast delivery using rapid development tools
  • Clarifies requirements before full-scale development
✅ Advantages ❌ Disadvantages
Users actively involved; better understanding Leads to "implement-and-repair" approach
Errors detected much earlier Scope creep — system complexity may expand
Missing functionality identified easily Incomplete problem analysis
Quick user feedback → better solutions Prototype may be mistaken for the final product
Boehm's Spiral Model
exam▶
Origin

Proposed by Barry Boehm in 1986 (also said 1988). Known as the Meta Model — combines characteristics of Waterfall, Incremental, and Evolutionary models. It is risk-driven.

Structure

The spiral model has a series of loops (spirals), one for each phase of development. Each loop is split into four quadrants/sectors:

Quadrant 1
Determine Objectives
Define objectives, constraints, management plan; identify risks and alternative strategies
Quadrant 2
Assess & Reduce Risks
Detailed risk analysis; develop prototype if required; resolve technical uncertainties
Quadrant 3
Development & Validation
Select a model based on risk evaluation; develop, test, and validate the system
Quadrant 4
Planning
Review and decide whether to continue; plan for next phases (schedule, cost, manpower)

Key Characteristics

  • Used for large and complex projects
  • Useful if requirements are frequently changing, unclear, or complex
  • Risk assessment built into every cycle
  • Cost estimation and software deployment are faster
  • More documentation due to many intermediate steps
✅ Advantages ❌ Disadvantages
Risk management features — risks identified early Not suitable for small projects
Flexible to changing requirements Risk assessment expertise required
Combines best features of multiple models More documentation — time consuming
Customer satisfaction built in May not meet schedule or budget
Evolutionary (Incremental/Successive Versions) Model
core▶

System is broken into modules incrementally implemented and delivered. Develop the core modules first, then refine into increasing levels of capability by adding new functionalities in successive versions.

  • Each successive version is a functioning system capable of performing some useful work
  • A new release may include new functionality AND enhanced existing functionality
  • Core modules get tested thoroughly → fewer errors in final product
Example: Library System (4 Iterations)

Iter 1: Login + book search → Iter 2: Book issue/return → Iter 3: Fine calculation + alerts → Iter 4: Performance + admin reports

✅ Advantages ❌ Disadvantages
Users experiment with partial system early Difficult to subdivide all problems functionally
Core modules thoroughly tested Best for very large problems; not suitable for all

Agile Methods — Overview
exam▶
Why Agile?

Plan-driven approaches had overhead — too much documentation, delays in planning/designing. Not suitable for small/medium projects or systems with frequently changing requirements. Agile methods emerged to address this.

Agile Manifesto Values

  • Individuals and interactions over processes and tools
  • Working software over comprehensive documentation
  • Customer collaboration over contract negotiation
  • Responding to change over following a plan

Five Core Principles

Principle Description
Client's Involvement Customers involved throughout; new requirements based on feedback
Incremental Delivery Small increments; every new requirement added per increment
People and Process Capacities of persons identified, work assigned accordingly
Address Changes Changes accommodated in the ongoing software
Simple Approach Less complex process; focus on software not the plan

Agile vs Plan-driven

Aspect Plan-driven Agile
Activities Planned with fixed, linear stages Done in iterations, parallel fashion
Documentation Heavy documentation at each stage Minimal; focus on design and implementation
Requirements Fixed before development starts Flexible; change as needed
Best for Large complex projects with stable requirements Small/medium projects with changing requirements

Applications well-suited for Agile

  • Small and medium software products
  • Customized products with fewer rules and regulations
  • Applications with customer transparency and flexible priorities
  • Continuous software delivery and improvement needed

Challenges with Agile

  • Client may not always be available to participate
  • Team members may struggle with intensive collaboration under pressure
  • Frequently changing priorities can cause delays
  • Simplicity requires extra effort; critical/safety systems need careful scaling

Agile Frameworks

Scrum · Kanban · Extreme Programming (XP)

Extreme Programming (XP)
exam▶
What is XP?

The most well-known agile development method. Called "extreme" because agile activities are pushed to an extreme level. Requirements are expressed as user stories and implemented as a set of tasks.

XP Process

User Stories → Tasks → Test → Release → Evaluate User Feedback → New User Stories → ... (repeated many times)

Key Features

  • Based on incremental development; user stories used as basis for new functions
  • Customers involved in acceptance testing of developed parts
  • Pair programming: People work in groups of two — exchange knowledge, check each other's work
  • New versions built many times per day
  • Increments delivered to customers every two weeks
  • Simplicity maintained throughout
XP is currently one of the most well-known ADLC models

XP = User Stories + Pair Programming + Frequent Releases + Test-Driven Development + Simple Design

Scrum Process
exam▶
Definition

Scrum is a method for software projects where there is continuous experimentation and response from clients. Software is developed in a series of increments called sprints (2 weeks to 2 months), in coordination of software engineers and clients. Introduced 1995.

Scrum Team Roles

  • Scrum Master: Organizes and coordinates the scrum; removes obstacles
  • Development Team: Group of developers creating the software project
  • Product Owner: Ensures the product meets all requirements; manages product backlog

Three Phases

  1. Initial Phase: Define the product backlog — all features/work to be done
  2. Sprint Cycle: Short iterations where teams develop, test, and deliver working software; each sprint has 5 events and 3 artifacts
  3. Closure Phase: Wrap-up, documentation, and retrospective

Key Features of Scrum

  • Product divided into smaller manageable parts
  • Each part managed by a team member
  • Development not held up even if requirements aren't fully defined
  • Entire team can view the production process; better communication
  • Customers see delivery during intermediate stages and give feedback
  • Trust built between clients and developers

Requirement Analysis — Introduction
definition▶
Requirement Engineering (RE)

The process of analyzing, searching, and documenting requirements. Determines the description of the problem, why it needs solving, the possible solutions, and the I/O of the system.

Types of Requirements

User Requirements

High-level abstract requirements written for end-users and clients — not related to software system development. Written in natural language.

System Requirements

Detailed description of the system functions, services, and operational constraints — related to how to develop the system considering the client's business.

Stakeholders and Requirements

Requirement Type Stakeholders
User Requirements System Architects, Managers (client-side), Contractors, Client Engineers, End-Users
System Requirements System Architects, Contractors, Client Engineers, End-Users, Software Developers
Functional vs Non-Functional Requirements
exam▶
Functional Requirements

Describe what functions the software system provides — how it should react to inputs and generate outputs. Also specifies what is NOT supported. Must be complete and consistent.

Hospital Management System — Functional Requirements Example

• List all clinics in the city
• Each clinic maintains appointment list for patients
• Each clinic maintains employee list with unique codes
• User can search by area, city, and specialty

Non-Functional Requirements

Not directly connected to functionality; related to other parameters. Often more critical — one non-functional requirement failure can make entire software useless (e.g., ATM security).

Category Types
Product Requirements Efficiency (performance, space), Dependability, Usability, Security
Organizational Requirements Environmental, Operational, Developmental
External Requirements Regulatory, Ethical, Legal (Safety and Security)

Metrics for Non-Functional Requirements

Property Metric
Speed Number of transactions per second
Size Number of bytes/memory chips
Ease of use Help options, time for training
Reliability Failure rate, availability
Robustness Recovery time after failure, data corruption probability
Portability Dependency on platform/OS
Requirement Engineering (RE) Process
exam▶

The RE process searches, analyzes, and verifies system requirements. It depends on the application, people, and organization. Four generic activities:

1. Feasibility Study

Takes place in the early stage. Answers: Does the system meet organizational objectives? Can it be implemented with existing technology? Can it integrate with existing systems?

Type 1
Technical Feasibility
Can the product be developed using existing technology? Can it be maintained?
Type 2
Operational Feasibility
Can it be operated/used easily? Can operations be maintained post-deployment?
Type 3
Legal Feasibility
Does it fulfill legal/ethical needs — copyright, license, security laws?
Type 4
Schedule Feasibility
Can the project be completed within the given deadline?

Feasibility Study Activities

  1. Introduction: Problem statement definition; background details; list of functions
  2. Summary & Recommendations: Customers, competitors, technical details, time estimates
  3. Alternatives: Current system vs. modification options; possible solutions
  4. System Description: Proposed solution; teams needed; equipment modifications
  5. Cost-Benefit Analysis: Project cost, initial investment, expected income, cash flow
  6. Evaluation of Risks: Legal, financial, operational risks; calculated decision
  7. Conclusion: Binary Yes/No decision on the new project

2. Requirements Elicitation and Analysis

Stakeholders collect information about domain, activities, services, performance, features, hardware/software conditions.

Sub-steps:
  • Requirements Discovery: Gather user and system requirements from all stakeholders
  • Requirements Classification and Organization: Group collected requirements
  • Setting up Priority and Negotiations: Resolve differences of opinion by prioritization
  • Requirements Documentation: Document as early draft of SRS document

3. Requirements Specification

Documents both user and system requirements — simple, unambiguous, well-documented. Used as a contract between client and software firm.

Ways to write system requirements:
  • Natural Language Specification: Expressive and universal but can be vague/ambiguous
  • Structured Specification: Standard form rather than free-form text
  • Graphical Notations: UML use-case and sequence diagrams
  • Mathematical Specifications: Formal notations based on finite-state machines or sets; unambiguous but customers struggle to understand

4. Requirement Validation

Verifies requirements fulfill the client's needs. Checks:

  • Validity checks: Do requirements meet real needs of system users?
  • Consistency checks: No conflicting requirements
  • Completeness checks: All functions and constraints defined
  • Realism checks: Can it be implemented within budget and technology?
  • Verifiability: Can tests be written for each requirement?
Validation Techniques:
  • Requirements Reviews: Team of reviewers checks for errors and inconsistencies
  • Prototyping: Executable model shown to end-users and customers
  • Test-case generation: Write tests for requirements; part of validation process
Challenges in Gathering Requirements

• Clients may not know what the system should do / demands may be unrealistic
• Complex patterns of interaction between users and analysts
• Some users unwilling to give requirements (fear of job replacement)
• Human information processing limitations and biases

Requirement Elicitation Techniques
core▶
Technique Description When Used
Interviewing Direct face-to-face or virtual discussion with stakeholders about their workplace, challenges, and constraints Early stages to gather high-level goals
Observation / Ethnography Analyst observes stakeholders performing daily tasks; documents how people actually work rather than formal methods When users can't clearly express requirements
Scenarios Real-life examples of how users would interact with the system; studied using interaction and information at different levels Understanding user-system interaction
Use Cases Graphical notations and structured text helping understand user interaction with the system Modeling specific workflows
Questionnaires Structured list of questions to find info from multiple sources; covers development, testing, and program management Gathering info from many people
Survey Captures responses (agree/disagree, Yes/No); closed or open-ended questions Collecting opinions from many users

Group Discussion / Focus Group People from similar backgrounds together to understand the problem domain; resolve conflicts in requirements Consensus on unclear requirements
Prototyping Sample/mock model expressing ideas; virtual digital model of system before development Expressing unclear requirements visually
Brainstorming Group activity generating new ideas; group leader manages opinions; ends with detailed requirement list document Creative requirement discovery
Software Requirements Specification (SRS)
exam▶
Definition

SRS is a systematically organized document containing all requirements for the software to be developed. The analyst collects all information, removes incompleteness and inconsistencies, and organizes into SRS. It serves as a contract between client and software firm.

Users of SRS

  • Customers/Users/Clients — giving information and changes
  • Managers — preparing project plan
  • System engineers — developing the system using requirements
  • Test engineers — validation of system with suitable data
  • Maintenance engineers — understanding requirements and system connection

Characteristics of a Good SRS

Characteristic Meaning
Correctness Covers all requirements of the system
Completeness Ready version of all requirements for submission
Consistency No ambiguity — no contradictory requirements
Concise Compact document — no unnecessary details
Unambiguous Only one interpretation of each requirement
Black-box view Implementation details hidden; only functional view given
Verifiable Requirements can be formally verified using scientific methods
Modifiable Can easily accept changes to the system
Traceable Design, software, and test cases can be traced for correctness
Testable Easy to generate test cases and test plans from the document

Characteristics of a Bad SRS

  • Over-specification: Too detailed — difficult to understand and use
  • Forward references: Uses terms not yet defined
  • Wishful thinking: Requirements that cannot be practically implemented
  • Noise: Unnecessary details included

IEEE SRS Standard Structure

  1. Introduction — Purpose, Project Scope, Definitions/acronyms, References, Overview
  2. Overall Description — Product perspective, features, user classes, operating environment, design constraints, user documentation, assumptions
  3. Specific Requirements — Functional requirements (use cases)
  4. External Interface Requirements — User, hardware, software, communication interfaces
  5. Non-functional Requirements — Performance, safety, security requirements
  6. Other Requirements — Database, legal, etc.
  7. Appendices — Glossary, Analysis Models, TBD List
Verification vs Validation (Boehm)

Verification: "Are we building the product right?" — Checks specifications, design, and code against standards; may not include execution.
Validation: "Are we building the right product?" — Ensures software meets client requirements; involves code execution.

Good Software Design — Principles & Characteristics
core▶
Design Phase

Begins after completion of requirement analysis. While requirements specify what the software should do, design specifies how to develop the system to meet requirements. Concentrates on the solution domain.

Why Design is Critical

  • Provides the basic framework guiding how code should be written and personnel assigned
  • Design errors are costlier than coding errors — take more time to detect and correct
  • Poorly designed software is often unreliable, inefficient, and not maintainable
  • Design becomes critical when systems become larger and many developers are involved

Characteristics of Good Software Design

Characteristic Meaning
Correctness Correctly implements all functionalities in the SRS
Understandability Easy to understand by all team members
Efficiency Time, space, and cost are optimized
Maintainability Simple and easy to maintain
Completeness Has all components — data structures, modules, external interfaces
Consistency No inconsistencies in the design

Software Design Activities (Phases)

  • Preliminary / High-Level Design: Identifies modules, control relationships, interfaces; produces program structure/software architecture
  • Detailed Design: Designs data structures and algorithms for each module; produces module-specification document

Key Design Principles

  • Modularity: Divide system into smaller, manageable modules
  • Abstraction: Focus on what a component does, not how; hide internal details
  • Information Hiding: Internal details of a module should not be exposed to others
  • Problem Partitioning / Divide & Conquer: Break problem into smaller subproblems to reduce complexity
  • Low Coupling & High Cohesion: Modules should be independent yet internally focused
  • Simplicity: Avoid unnecessary complexity
  • Portability: Design can be used on different platforms
  • Flexibility: Accommodates changes in the system
  • Reusability: Components can be reused to develop new software
Top-Down vs Bottom-Up Design
exam▶
Aspect Top-Down Design Bottom-Up Design
Approach Starts with general solution → divides into sub-solutions/subsystems; each further divided Lowest-level subsystems and components designed first; combined into next abstraction level
Used when Design is to be formed from scratch/ground level An existing software system exists and a new system is to be formed based on it
Flow Whole system → sub-systems → components Components → sub-systems → whole system
Example Online Shopping System → User module → Product module → Cart module → Payment module → Delivery module Database Access + Utility → Reports → User Interface
In Practice

Top-down is preferred for new systems built from scratch. Bottom-up is preferred when reusing existing components or building on a legacy system.

Functional vs Object-Oriented Design
exam▶
Functional / Structured Design

Design divided into a collection of units based on function. Each unit has a dedicated task. Three steps: Data flows design (DFDs) → Structure division (structure charts) → Detailed design (data dictionary).

Object-Oriented Design (OOD)

System viewed as a collection of objects. Object = entity in a solution (office, user, school, shop). Described using a class — an abstract data type with attributes and methods. Object is an instance of a class. OOD gives more importance to data than algorithms.

Aspect Functional Design OOD
Focus Functions with dedicated tasks Objects and classes
Primary elements Variables and functions (cannot be altered) Objects and methods (can change data)
Priority Algorithm/method more important than data Data more important; method can change based on data
Iteration Recursion used more frequently Iterative method used
Data hiding Not possible; no adding data randomly Possible via private/protected access
Statement order No particular order Bottom-up order used
Data Flow Diagrams (DFDs)
core▶
DFD Definition

A graphical representation showing how data flows through a system, where it is stored, and how it is processed. Focuses on data movement (inputs, processes, outputs) rather than physical details. Formula: Who sends data → Where it goes → How it's processed → Where it's stored.

DFD Entities (Four Symbols)

  • External Entities: Data originators or receivers (outside the system)
  • Processes: Data transforms (shown as circles/rectangles with rounded corners)
  • Data Flows: Movement of data (arrows)
  • Data Stores: Where data is held (open-ended rectangles)

Levels of DFDs

Level Name Description
Level 0 Context Diagram Presents an overview of the system as a single process with external entities; bird's-eye view
Level 1 1-Level DFD Breaks main process into sub-processes; shows how data flows internally in more detail
Level 2+ Detailed DFDs Further breakdown of Level 1 processes; used for complex systems only
DFD Design Tips

A data dictionary tool is used in detailed design alongside DFDs to describe the data elements. DFDs are the foundation of structured analysis and design.

Cohesion — Types and Classification
exam▶
Cohesion

Cohesion is a measure of the functional strength of a module. It measures how closely related the responsibilities of a single module/class/function are. Higher cohesion = better design. It groups things that make sense together.

Types of Cohesion (from least to most desirable)

Type Description Example
Logical Cohesion All elements perform similar operations print() function printing student attendance, teacher attendance, student marks — all are "printing" but unrelated
Temporal Cohesion All functions execute at the same time Start, shutdown, sleep, initialize functions of a process executed together at system startup
Procedural Cohesion All functions are part of the same algorithm/working toward a common goal Enter user ID, password, and captcha — parts of authorization goal
Communicational Cohesion All functions refer to or update the same data structure add(), delete(), print(), modify() working on STUDENT database
Sequential Cohesion Elements form a sequence; output of one is input to the next Insert card → Enter PIN → Authorize — ATM functions
Functional Cohesion ⭐ All elements work together to achieve a single task — Most desirable Select cabin class / choose seat preferences — all related to seat_allotment module in airline reservation
High vs Low Cohesion Example

High Cohesion: Student module with Name, RollNo attributes and PrintRecord(), PrintResults(), PrintAttendance() — all related to student data.
Low Cohesion: Module with CheckEmail(), Print(), PrintStafflist() — unrelated functions mixed in one module.

Coupling — Types and Classification
exam▶
Coupling

The coupling between two modules is a measure of their interaction. Lower coupling = better design. Good software should have as independent modules as possible. Reduces complexity, improves performance and reusability.

Types of Coupling (from most desirable to least)

Type Description Example
Data Coupling ⭐ Two modules communicate using a common parameter (simple data) Bank application passing account number between modules
Stamp Coupling Two or more modules use composite data (entire data structure passed) Struct in C or classes/objects in C++ passed between modules
Control Coupling Data from one module used to direct the order of instructions in another draw() passes "circle"/"square" command to control which function to call
Common Coupling Two modules share information through global data items Student management with multiple modules sharing a global STUDENT data structure
Content Coupling ❌ More than one module shares code; branch from one module to another — Worst/Most undesirable menu() directly calling add(), subtract(), mult(), div(), print() — direct code sharing
Key Rule for Exam

High Cohesion + Low Coupling = Good Design. A functionally independent module performs a single task without much interaction with others. This leads to better error isolation, more reuse, and improved understandability.

UML — Introduction & Overview
exam▶
UML Definition

Unified Modeling Language (UML) is a general-purpose visual modeling language. Its main aim is to define a standard way to visualize how a system has been designed — similar to blueprints in other engineering fields. UML is NOT a programming language — it is a visual language.

Why OOD and UML?

OOD is a programming technique that solves problems by building a system of interrelated objects. Uses concepts of classes, objects, encapsulation, inheritance, and polymorphism to model real-world entities and interactions.

Two Categories of UML Diagrams

Diagram Purpose

Deployment Diagram Shows system hardware and its software; represents system architecture
Package Diagram Organizes classes into packages (namespaces)
Behavioral Diagrams (Dynamic)
Diagram Purpose
Use Case Diagram Shows user interaction with system (actors and use cases); high-level view of functionality

Communication Diagram Similar to sequence but simpler; focuses on relationships
Class Diagram
core▶

A UML class diagram visually represents the structure of a system by showing its classes, attributes, methods, and relationships. Helps developers and designers understand how the system is organized and how components interact.

Class Box Structure

  • Top compartment: Class name (centered, bold)
  • Middle compartment: Attributes/properties (with visibility and data type)
  • Bottom compartment: Methods/operations (with visibility, return type, parameters)

Visibility Notation

  • + Public — visible to all classes
  • - Private — visible only within the class
  • # Protected — visible to subclasses
  • ~ Package/Default — visible to classes in same package

Use Case, Sequence & Activity Diagrams
core▶
Use Case Diagram

Depicts the functionality of a system or part of a system; shows interaction with external agents (actors). Gives a high-level view of what the system does without going into implementation details. A use case represents different scenarios where the system can be used.

  • Actor: External entity that interacts with the system (user, device, other system)
  • Use Case: Specific functionality or service provided by the system
  • System Boundary: Rectangle showing what's inside/outside the system
Sequence Diagram

Depicts interaction between objects in a sequential order — the order in which interactions take place over time. Shows how objects function and in what order messages are passed. Widely used by both businessmen and developers to document and understand requirements.

  • Objects shown across the top; time flows downward
  • Messages shown as arrows between objects
  • Lifeline shows object's existence over time
Activity Diagram

Shows step-by-step flow of activities or workflow. Similar to a flowchart but with support for parallel activities, decision points, and swimlanes (showing who does what).

Exam Tip

Use Case = who interacts with what. Sequence = in what order messages flow. Activity = step-by-step workflow. State = how an object changes states.

Introduction to Coding & Software Implementation
core▶
Definition

Software Implementation/Development/Coding is the process of converting the design of a system into a high-level language program. It results in an executable version of the software. Coding guidelines are defined by the organization; different tools (compilers, debuggers, interpreters) are used.

Important Aspects to Consider in Coding

  • For what application is the software being used?
  • Use of new technology
  • Time necessary for software launch
  • Scalability, Security features, Tool availability, Efficiency
  • Reuse of the software (COTS — Commercial Off-The-Shelf)
  • Managing configuration of the software

Software Reuse — Levels

COTS (Commercial Off-The-Shelf) components are readily available, can be bought and modified. Reuse reduces time and cost. Levels:

Level What is Reused Example
Abstraction Level Architecture and design patterns MVC pattern reused across projects
Component Level Front ends, GUI, tables, database structures Reusing login component
Object Level Existing library files, objects, and files Using Java Collections library
System Level Entire existing system modified and refined Student record software modified for a new college

Configuration Management

A process of managing changes during software development when a team of people is working. Three main activities:

  • Version Management: Keeping track of different versions of software
  • System Integration: Support for combining different version components into a single system
  • Problem Tracking: Tools for error detection and correction
Standard Coding Requirements

• Modular approach — easier to understand and debug
• Common, familiar notations for all developers
• Portability and generality without rigid constraints
• Efficient error checking and exception handling
• Concise code — faster execution, less memory

Coding Guidelines
exam▶

Coding guidelines provide common knowledge for using coding style. The actual implementation is up to the individual, but guidelines ensure uniformity and quality. If coding standard is not maintained, code might get rejected in code review.

Key Coding Guidelines

  • Size: Code should be small and easy to understand. Functions >10–15 lines defeat the purpose of modularity and make error detection very challenging.
  • Variable Scope: Clarify global vs. local variables (block/file scope) to limit access to different users in the system.
  • Module Documentation: Include module name, author, date of creation, brief synopsis, modification details — in guidelines documents.
  • Naming Conventions:
    • Variables: alphabets, digits, underscores (e.g., Student_Name)
    • Constants: all capitals (e.g., MAX)
  • Error Handling: Return 1 or 0 based on conditions → uniform, reusable style.
  • Avoid go-to statements: Unconditional jumps make programs difficult to understand and debug.
  • Meaningful variable names: Use temp_loan_value over just temp.
  • Side effects: A side effect of a function is modification of parameters outside its definition. I/O operations or pass-by-reference may create ambiguous alterations.
Code Documentation
core▶
Purpose

Coding documentation is an effective means of connecting humans and machines. Helpful to developers working on long-term projects, allows others to continue work further, shows contributions, and promotes open-source software transparency.

Major Steps in Software Documentation

  1. README file: Brief introduction — installation procedure, OS, hardware requirements, sample usage
  2. Module functionality: Parameters, their types, and return values for each module
  3. Naming conventions: Files, variables, constants, programming practices, comments on database/web-based apps used
  4. Contributors: Name contributors in a team and their part with proper citations
  5. License and version: License details and version of the software developed
  6. Developer roles: Names and email addresses for future contact
  7. Version history: Current version and editing performed
Code Review — Purpose and Process
exam▶
Code Review

Done after compilation of a coding module. Detects algorithmic, logical, and poor programming issues. Does NOT check syntax errors. Different from testing — review is on non-executable code. Performed by developers, testers, or quality control managers.

What Code Review Checks

  • Are requirements covered in various test cases?
  • Is the software design consistent?
  • Is the developed code following the standard coding style?
  • Are there enough test cases to verify the developed software?
  • Are there any security threats?
  • Is code documentation complete?
  • Any major flaws — insufficient memory, data issues, overflow/underflow?
  • Are syntax and logical errors handled?
  • Are there performance defects?

Benefit of Early Code Review

Errors identified at the beginning stage means less time-consuming debugging in later stages.

Code Walkthrough vs Code Inspection
exam▶
Aspect Code Walkthrough Code Inspection
Purpose Find algorithmic and logical errors Find common programming errors (does not execute code)
Process Each team member uses sample test cases; traces code manually for different test cases Reviews programming practice, algorithm choice, library usage, coding standard
Presence Done in the presence of the coder who developed that code Independent review; coder may not be present
Formality Informal — relies on experience, knowledge, common sense More formal — checks specific error categories
What is found Whether code is working and producing desired results Infinite loops, memory allocation, type mismatch, wrong operator precedence, out-of-bound arrays, dangling pointers
Output Minutes of walkthrough recorded and used as coding guidelines List of specific errors and coding standard violations
Key Difference

Walkthrough: Code execution performed (with test data) to check results. Inspection: No execution — reviews the way of programming and looks for known error patterns.

Testing Fundamentals — Errors, Bugs, Faults & Failures
exam▶
Two Goals of Testing

1. To illustrate that the developed software fulfills client's requirements.
2. To search for scenarios and data where software may not work as per specification or may result in an error or corrupt data.

Key Terminology

Term Definition Example
Error A human mistake made during software development (wrong design decision, wrong logic) Developer writes area = length + breadth instead of length * breadth
Fault / Bug / Defect Manifestation of an error in the software artifact. A bug may be due to algorithm, resources, or logic Missing validation for division by zero; incorrect database schema
Failure System doesn't perform as expected; produces incorrect/unexpected results — when users actually see the problem Banking app calculates interest incorrectly; game freezes at level 50
  • Defects can be major, critical, or minor
  • System leads to failure if there are multiple defects
  • Bug is the everyday industry term (loosely used for error, defect, or failure)

Test Case and Test Suite

A test case is a triplet [I, S, O]: I = input data, S = system state at input time, O = expected output.

A test suite = set of all test cases.

Important

Randomly selecting many test cases does NOT guarantee finding errors. A large test suite is NOT an indication of effectiveness. Systematic approaches are required — each test case should detect different errors.

SUT

The software under test is known as SUT.

Verification vs Validation
exam▶
Aspect Verification Validation
Question "Are we building the product right?" "Are we building the right product?"
Checks Output of one development phase conforms to previous phase; specs, design, code checked Fully developed system conforms to its SRS document
Code execution May NOT include program execution; static tests Always involves execution of code
Target Source code, design documents Always the code
Performed by System analysts and designers Software development team (and end-users in acceptance testing)
Techniques Code inspections, reviews, walkthroughs Unit testing, integration testing, system testing
Phase Early stages — high-level design, database design After verification of the code
V & V Technique

Requirement specifications, design models, code, and proposed tests are checked. The objective is to develop confidence that the software system is fit for its purpose. Level of confidence depends on system's purpose — safety alarm needs higher confidence than a text editor.

Levels of Testing
exam▶

Three Stages of Commercial Testing

  • Development Testing — includes system designers and developers; checks for errors during development
  • Release Testing — functional testing by development team to convince supplier it's good enough; tests requirement-based, scenario-based, performance-based, regression
  • User Testing — end-users test system in real environment; acceptance testing

Unit Testing

Done in the coding and development phase. Tests the smallest element of software (module) in isolation. Each module tested separately before combining. Helps correct errors at early stage.

  • Checking loops, functions working in a program
  • Checking initialization values, operator precedence

Integration Testing

Different modules integrated using a software plan; checks the steps and sequence by which different modules form a single system.

Approach Description Notes
Top-Down Higher/main modules tested first; lower modules use stubs (small dummy programs substituting for lower modules) Main control tested early; stubs used for incomplete lower modules
Bottom-Up Lower modules tested first; drivers used as dummy main modules if higher modules not ready Detailed functionality tested first
Big-Bang All modules simply put together and tested at once Useful for small systems; error handling very difficult; high-risk modules not prioritized
Sandwich/Mixed Combination of top-down and bottom-up; tests as modules become available Used in large systems; expensive; not suitable for high coupling

System Testing (User Testing)

Done by users entering input in real environments; tests usability and reliability. Includes non-functional characteristics (volume, stress, compatibility, configuration). Classified as Alpha and Beta testing.

  • Smoke Testing: Quick test to check if the build is stable (e.g., launch app and check login)
  • Sanity Testing: After a bug fix, verify the change didn't break functionality
  • End-to-End Testing: Simulate real user flow (login → enroll → quiz → grade)
  • Happy Path Testing: Only valid inputs and expected flow
  • Monkey Testing: Random inputs to find crashes

Alpha Testing

Done in the early stage of software development to identify defects before final release. Performed by internal team/high-level developers. Example: Google releasing new feature to high-level developers first.

Beta Testing

Beta version given to limited users to test and improve quality. Users experiment and raise problems for developers. System tested with real data and environment. Example: Software company releases to a few small colleges for feedback before wide release.

Acceptance Testing

End-users test the system and decide if it's ready for deployment. Last phase of software testing — after acceptance testing, payment can be done to developers. Includes:
• Alpha: Done by internal team before release
• Beta: Done by end users before final release
• UAT (User Acceptance Testing): Formal validation by client/user

Regression Testing

Testing when an existing system is changed or upgraded. Checks for new bugs after addition of new features or performance issues. Only test cases that can affect changed functions need to be run. Performed in the maintenance stage.

Gorilla Testing

Repeatedly testing one module/function intensely to ensure reliability. Example: Testing "Login" feature with thousands of valid/invalid combinations.

White Box Testing
exam▶
White Box / Clear Box / Glass Box / Structural Testing

Tests the internal logic, structure, and flow of the code. Tester understands the code and inner workings. Performed by the software developer (not the test engineer). Tests: loops, data flow, code coverage, each statement, security holes.

Methods in White Box Testing

Method Description Drawback/Note
Statement Coverage Every statement in the program executed at least once. Checks for mistakes in computation, unused statements, missing branches May work properly for one set but not for others
Branch Coverage Each conditional branch tested for true and false values. Also called edge testing. Stronger than statement coverage Guarantees all test cases fulfilled
Condition Testing Used when there's more than one condition or composite condition. For n expressions, 2ⁿ test cases required Exponential growth in test cases
Path Testing Tests control paths of the program depending on if, if-else, loops. Requires complete knowledge of the program Values of different variables can be traced
Data-flow Testing Uses definitions and uses of variables as test paths. Points out undeclared variables, deleting memory before use, multiple declarations Good for detecting variable-related bugs
Mutation Testing Some statements of source program changed ("mutated") to verify test cases can locate errors. Changed program = mutant. If output differs → mutant is "killed" Changes: data type, constant value, operator order
Black Box Testing
exam▶
Black Box / Functional / Behavioral Testing

Tests functionalities of software using requirement specifications — without knowledge of design or code. Tests behavior visible from outside. E.g., testing websites like gmail.com, irctc.in, makemytrip.com.

Black Box Testing Steps

  1. Examine the requirement specifications of the system
  2. Select a set of proper inputs and determine the possible output
  3. Prepare test cases for inputs and execute them
  4. Compare results with expected outcomes
  5. If undesired results/errors found, correct and repeat testing

Black Box Testing Techniques

Equivalence Partitioning

Input values partitioned into equivalence classes where the program behaves similarly to every input in the class. Test with one representative from each class — as good as testing any other value in the class.

  • If input specified by a range (1–5000): 1 valid class + 2 invalid classes (negatives, >5000)
  • If input is an enumerated set {a,b,c}: 1 valid class + 1 invalid class
Example

SQRT program for integers 1–5000: Classes are {negative integers}, {1–5000}, {integers >5000}. Test suite: {-5, 500, 6000}

Boundary Value Analysis (BVA)

Typical programming errors occur at the boundaries of equivalence classes (psychological factors — programmers use < instead of ≤). Select test cases at boundaries.

  • For SQRT (1–5000): Test values {0, 1, 5000, 5001}
  • For age eligibility (18–60): Test values {17, 18, 60, 61}
Decision Table Testing

Conditions mentioned under certain conditions in the form of decision tables. Good for complex business rules.

State Transition Testing

Tests transitions of states from one form to another. Good for systems that change states based on events (e.g., order: draft → submitted → approved).

Technique White Box Black Box
Knowledge needed Internal code and logic Only functional specifications
Performed by Software developer Test engineer or user
What's tested Code structure, paths, coverage Functionality and behavior
Also called Clear/Glass box testing, Structural testing Functional/Behavioral testing
Software Project Management (SPM) — Introduction
core▶
SPM Definition

Software Project Management is the process of managing software projects within allocated budget and time constraints. The project manager takes responsibility for delivering a project that meets client requirements and is of high quality.

Goals of SPM

  • Maintain the agreed timing of software delivery
  • Keep project activities under the allotted budget
  • Fulfill the client's specifications
  • Ensure the development team is functioning well in a positive atmosphere

SPM Activities

  • Project Planning: Project manager plans, estimates, develops schedule, allocates tasks; must be done before development begins
  • Project Monitoring and Control: Ensures development proceeds as per plan; changes plan based on situation; includes risk management and people management

Project Planning Estimates

  • Size: Complexity in terms of efforts and time (LOC, Function Points)
  • Cost: Finance necessary to complete the project
  • Duration: Time required for completion
  • Efforts: Manpower and other resources required

Documented in the Software Project Management Plan (SPMP) document.

The Management Spectrum (Pressman)

  • People: Team management, roles, motivation
  • Product: Understanding what's being built
  • Process: The framework for development
  • Project: Planning, scheduling, tracking
Size Estimation — LOC and Function Points
exam▶

Lines of Code (LOC)

Simplest metric — counts number of source instructions. Comments and header file statements are excluded. To estimate LOC at initial stages, project is divided into modules and sub-modules.

Skill-Level Based LOC Formula
Expected LOC Formula
S = (Sopt + 4 × Sm + Spess) ÷ 6

Where: Sopt = Optimistic (efficient developer), Sm = Most Likely (average), Spess = Pessimistic (poor developer)
Worked Example

Sopt = 5200, Sm = 7000, Spess = 9000
S = (5200 + 4×7000 + 9000) / 6 = 42200/6 = 7033 LOC

With 2-person team: 24 person-months total
Productivity = 7033/24 = 293 LOC/person/month

If duration = 6 months: Manpower = 24/6 = 4 persons
If cost = ₹2500/person-month: Development cost = 24 × 2500 = ₹60,000

LOC Advantages and Limitations
  • ✅ Easy to estimate; commonly used
  • ❌ Doesn't consider complexity — number of I/O, files, interfaces, functions
  • ❌ Less efficient due to dependency on programming language

Function Points (FP)

Proposed in 1983. Measures size of software based on functional view. Considers: number of inputs, outputs, queries, internal files, and external files. Overcomes many pitfalls of LOC. Can be used from the problem specification stage (unlike LOC).

  • Functionality measured based on user's request and response
  • Cost estimation independent of technology
  • Requirements can be verified using function count
  • ❌ Uses much judgment which may not be accurate
  • ❌ Less research on FP compared to LOC; time-consuming
COCOMO Model — Basic, Intermediate & Complete
exam▶
COCOMO — COnstructive COst MOdel

Proposed by Barry Boehm in 1981 after studying 63 projects. Based on LOC. Estimates size, effort, cost, time, and quality.

Three Project Categories (Boehm)

Category Description Size Range Example
Organic Well-understood project; small team with good experience; simple problems 2 KLOC – 50 KLOC Batch data processing, payroll
Semidetached Mix of experienced and inexperienced team; utility programs 50 KLOC – 300 KLOC Transaction systems, compilers
Embedded Strongly connected to complex hardware; complex projects with restricted regulations > 300 KLOC Real-time control systems, avionics

Basic COCOMO Model

Gives an approximate estimate. Uses KLOC as the estimated size.

Basic COCOMO Formulas
Effort: PM = a₁ × (KLOC)b₁ (Person-Months)

Dev Time: Tdev = a₂ × (PM)b₂ (Months)

Staffing: Average Staff = PM ÷ Tdev

Productivity: = KLOC ÷ PM (KLOC per Person-Month)
COCOMO Constants Table
Mode a₁ b₁ a₂ b₂
Organic 2.4 1.05 2.5 0.38
Semidetached 3.0 1.12 2.5 0.35
Embedded 3.6 1.20 2.5 0.32
📋 COCOMO Formula Cheat Sheet (Memorize This)

Effort: PM = a₁ × (KLOC)^b₁  →  Person-Months
Dev Time: Tdev = a₂ × (PM)^b₂  →  Months
Staff: Average = PM / Tdev  →  Persons
Productivity: KLOC / PM  →  KLOC per Person-Month

Organic: a₁=2.4, b₁=1.05, a₂=2.5, b₂=0.38
Semidetached: a₁=3.0, b₁=1.12, a₂=2.5, b₂=0.35
Embedded: a₁=3.6, b₁=1.20, a₂=2.5, b₂=0.32

Worked Example — Assignment Q1

32 KLOC, Organic mode (a=2.4, b=1.05, c=2.5, d=0.38)

Effort: PM = 2.4 × (32)1.05 ≈ 2.4 × 37.88 ≈ 90.9 Person-Months
Dev Time: T = 2.5 × (90.9)0.38 ≈ 2.5 × 9.22 ≈ 23.05 Months
Average Staffing: 90.9 / 23.05 ≈ 3.94 ≈ 4 persons

Intermediate COCOMO Model

Basic COCOMO only uses LOC, but in practice many other factors matter. The Intermediate model introduces cost drivers (multipliers) such as:

  • Experience and capability of team members
  • Reliability requirements
  • Hardware performance constraints
  • Use of software tools and development environment

Effort = Basic Effort × Product of all cost driver multipliers (EAF — Effort Adjustment Factor)

Complete (Detailed) COCOMO Model

Basic and Intermediate COCOMO treat the software product as a homogeneous entity. Most large systems have many smaller sub-systems with different types (organic, semidetached, embedded). Complete COCOMO:

  • Considers each subsystem separately and estimates effort for each
  • Total effort = sum of estimates for all individual subsystems
  • Applied in each phase of software engineering
Six Phases of Detailed COCOMO
  1. Planning and requirements
  2. System design
  3. Detailed design
  4. Module code and test
  5. Integration and test
  6. Cost Constructive model
MIS Example (Complete COCOMO)

Distributed MIS for an organization with: GUI (organic) + Database (semidetached) + Communication (embedded). Total cost = sum of individual sub-system estimates.

Advantages of COCOMO

  • Transparent — helps understand impact of different factors on project costs
  • Includes lessons from past projects
  • Drivers help understand impact of hardware, persons, software tools, and development atmosphere
  • Easy to use for cost estimation

Project Scheduling — Network Analysis

For complex projects, activities have predecessors. Calculate:

Critical Path Method (CPM) Formulas
ES = Early Start = max(EF of all predecessors)
EF = Early Finish = ES + Duration
LF = Late Finish (from backward pass)
LS = Late Start = LF − Duration
Slack = LS − ES = LF − EF
Critical Path = Path with Slack = 0

Software Quality Concepts & Attributes
core▶
Quality Software Definition

Defect-free software, delivered within the allocated budget and time, meets the client's requirements, and can be easily maintained. Just meeting specifications is not enough — if it works but is slow and uses excessive memory, it is NOT quality software.

Three Levels of Quality Concerns

  • Organizational Level: Process and standards defined by the organization for quality (collecting requirements, design standards, code standards)
  • Project Level: Quality processes applied to meet standards; quality plan developed with project goals
  • Individual Level: Adherence to coding and documentation standards

Quality Assurance (QA) vs Quality Control

A separate QA team is formed (different from development team) to define quality without development issues influence. Each developed part (D1, D2, D3...) is subjected to quality analysis with proper plan and expected standards.

Quality Plan Structure

  • Product Introduction: Features, benefits, specifications, target audience
  • Product Plan: Strategy and tactics for launching and supporting the product
  • Process Description: Development and service processes used
  • Quality Goals: SMART goals aligned with project objectives
  • Risk Management: Key risks (technical, schedule, cost, quality) and mitigation

Software Quality Attributes

Attribute Description
Safety and Security No harm caused; preventing unauthorized access/illegal activity
Reliability Performs intended functions without errors or failures consistently
Portability Works on different OS environments, systems, platforms
Usability Both expert seniors and new users can use without difficulty
Reusability Different components can be reused to develop new software
Modularity Divided into smaller modules; developers can work in parallel
Maintainability Easily corrected; new functions added without much overhead

Software Standards

Process Standards Product Standards
Define good software development processes Applied during development of software product
Covers SDLC stages, tools, documentation Structure of requirement specification document, coding standards, programming language standards
Example: Design review conduct, version release process Example: Design review form, Java Programming Style, Project Plan Format
ISO 9000 Certification
exam▶
ISO 9000

International Standards Organization (ISO) is an international standard development organization composed of national standards organization representatives. Published its 9000 series in 1987. Provides guidelines for maintaining quality; serves as a reference for contracts. Gives guidelines for producing the product — NOT concerned with the product itself.

Types of ISO 9000

Standard Applies to
ISO 9001 Most software organizations — design, development, production, and servicing
ISO 9002 Organizations NOT involved in design but only in production (car/steel manufacturing); does NOT apply to software
ISO 9003 Organizations involved ONLY in installation and testing of products

Why ISO Certification?

  • Customer gets confidence in the product
  • Well-structured and documented process assures high quality
  • Development process is more efficient and cost-effective
  • Weak points identified and remedies given
  • Sets basic framework for efficient process → Total Quality Management (TQM)

Limitations of ISO 9000

  • Sets steps for production process but does NOT guarantee high quality
  • Not a foolproof agency; may downplay domain experts
  • Heavy emphasis on documentation — takes time and effort
SEI Capability Maturity Model (CMM)
exam▶
SEI CMM

Used by the Software Engineering Institute to improve software quality. Two uses: (1) Capability Evaluation — assess software process capability of an organization; (2) Software Process Assessment — improve process capability.

Five Maturity Levels

Level Name Focus Key Process Areas (KPA)
Level 1 Initial Competent people; ad-hoc processes; unpredictable results None (chaotic)
Level 2 Repeatable Project Management; basic processes established Software project planning, configuration management
Level 3 Defined Defining of processes; organization-wide standards Process definition, training programs, peer reviews
Level 4 Managed Product and process quality; quantitative control Software metrics and quality management
Level 5 Optimizing Continuous process improvement; defect prevention Defect prevention, process change management, technology change management
CMM Key Point

Quality is improved gradually from one level to the next. Each stage is carefully designed so that one stage enhances the already existing capability. Moving from Level 1 to Level 5 is a journey of years, not months.

CMM vs ISO Comparison

ISO 9000: Certification-based; yes/no compliance; focused on documentation and processes; international standard.
CMM: Maturity-level based (1–5); focused on continuous process improvement; specifically for software; developed by SEI.

Software Maintenance — Definition and Types
exam▶
Definition

Software maintenance is a general process of modifying a software product after it is delivered to the client. The modifications are necessary to correct coding bugs, accommodate major design changes, and manage new requirements. The development of software does NOT end after its delivery.

Need for Software Maintenance

  • Technology changes rapidly; customers demand advanced features
  • Hardware configuration changes require interface modifications
  • Critical faults need repair to continue normal operations
  • Competitors add advanced features → software must compete
  • Legacy systems need to be migrated to new platforms

Legacy System

Old system with outdated hardware/software still in use. Software maintenance mitigates such systems: saving files in printed form, transferring to cloud/virtual machine, upgrading existing software, or discarding the existing system.

Examples of Maintenance

Patching in Windows/Apple/Linux. Updates in commercial antivirus software. Updates in typesetting software like Adobe, MS Office.

Types of Software Maintenance

Type Description Trigger
Corrective Corrects faults and errors reported by customers after system is put in use. Errors may be in requirements, design, or code. Customer bug reports; system failures
Adaptive Used when software environment changes — new OS, new web/mobile platform, new hardware added to existing system. Environment changes (new OS, new hardware)
Perfective Advancing requirements and features; adding new requirements user realizes after delivery; removing unwanted features; enhancing UX. User requests new features; system improvement
Preventive Future problems prevented using modifications and updates. Helps increase software lifetime. Code optimized to handle future environment changes. Proactive improvement; stability and maintainability
Forward Engineering, Reverse Engineering & Re-engineering
exam▶

Forward Engineering

The standard software development approach — follows steps in order:

Forward Engineering Process
Requirement Gathering → Preparing Software Design → Coding → Testing → Maintenance

Reverse Engineering

Definition

The process of recovering the design, requirement specifications, and functions of a product from an analysis of its code. Used for legacy systems that are not well-structured or lack documentation.

Steps in Reverse Engineering
  1. Code Improvement: Improve readability and structure; give meaningful names to variables and data structures; simplify complex statements; replace nested loops. These are "cosmetic changes" — functionality NOT changed.
  2. Code Analysis: Complete analysis of modules and their interfaces
  3. Design Extraction: Extract design using tools — structure charts, DFDs, control flow diagrams
  4. SRS Writing: Write the SRS document based on the extracted design

Software Re-engineering

Definition

When requirements change considerably, the amount of rework increases. A combination of reverse engineering followed by forward engineering is called software re-engineering. Legacy products are reverse-engineered to get module specifications, which are used to generate design, then explore requirements, add new requirements, and build with forward engineering.

Re-engineering Process
Legacy Code → Reverse Engineering → Module Specifications → Design → New Requirements Added → Forward Engineering → Improved Product
Software Re-engineering — Reverse + Forward Engineering Combined
When is Re-engineering Used?
  • Already developed software shows a high failure rate
  • Legacy products with very poor design and code structure
  • When documentation is missing or inadequate
Aspect Reverse Engineering Re-engineering
Direction Code → Design → Requirements Code → Design → Requirements → Code (combined)
Purpose Understand/document an existing system Transform an existing system into a new improved one
Output Documentation, design Improved software product with new requirements

SCM Definition

Software Configuration Management maintains the status of the software product and keeps account of changes. Configuration refers to the state of source code, design, SRS, test reports, user manuals used by software engineers during SDLC.

Types of Changes in Software Configuration

  • Release: Software released newly if there is a new bug fix, functionality, or small usage/technology changes. Example: Windows patches.
  • Version: Major change in hardware/technology or drastically changed functionality. Example: Android updates, Windows 95 → XP → 10.
  • Revision: Minor bugs or errors. Example: MS Office minor typesetting revisions.

Why SCM is Needed

  • If multiple engineers work on the same object without coordination → inconsistent objects → bugs
  • If software is modified by several people simultaneously → overwriting of code → integrity loss
  • If one developer is integrating while another is modifying → integration must be redone

SCM provides a freeze option — stabilizes the environment for development. Archives different variants of modules and provides the respective version to developers.

SCM Process Activities

  1. Configuration Identification: Objects classified into controlled (already configured), pre-controlled (will be configured), and uncontrolled (not subjected to control). Typical controllable: SRS, design, source code, test cases, reports.
  2. Version Control: Tools and methods to create different versions of objects, each with different features/attributes.
  3. Change Control: Requests for variation received; impact analyzed on functions and cost. Change Control Authority (CCA) — single person/team — authorizes or rejects changes. Also includes:
    • Access control policy — checks authority to change configuration
    • Synchronization control policy — prevents overwriting by multiple persons on a single object
  4. Configuration Audit: Checks whether original requirements are fulfilled in the new deliverable. Generates audit reports for stakeholders (developer, tester, customers) with FAQs, manual, installation guide.
  5. Status Reporting: Generates reports on current configuration status for all stakeholders.
CASE Tools (Computer Aided Software Engineering)

CASE Tools

CASE tools provide automated support in software engineering for all activities: gathering requirements, preparing software design, developing code, testing, configuration, and project management. Different from a programming environment — covers ALL phases of SDLC.

Types of CASE Tools Based on Phase

Type SDLC Phase Description Examples
Upper CASE Requirement collection, Planning, Analysis, Design Support early stages of SDLC Accept 360, CASE Complete
Lower CASE Coding, Testing, Maintenance Support later stages of SDLC Eclipse, Cscope (code search), SoapTest
Integrated CASE All stages Support all phases including documentation Rational Rose, Visual Paradigm
CASE Tools Classification — Upper, Lower & Integrated CASE

CASE Tools by Application

Application Description Examples
Prototyping CASE tools (Requirements) Understand user interaction, data storage, control flow during requirement collection Accept 360, CASE Complete
Structured Analysis & Design CASE tools Draw software design diagrams with less effort; support UML use-case, sequence diagrams, DFDs Flowchart makers, UML tools
Code Generation CASE tools Generate database tables, interfaces, records, or outer skeleton of software; NOT direct code writing Eclipse, Cscope, Adobe Edge Inspect
Test Case Generation CASE tools Support testing of requirements and design; generate test plans; enable regression testing SoapTest (validates functions, unit testing, functional testing)

Central Repository

CASE tools are collectively stored as toolkits in a common environment. Tools with common information integrated into a central repository. E.g., data dictionary can be used as CASE tool for storing elementary and composite data.

CASE Tools — Advantages and Limitations

  • ✅ Cost savings of 30-40% at different phases of SDLC
  • ✅ Better quality — already tested components
  • ✅ Consistent documentation generated
  • ✅ Fewer chances of human error (central repository)
  • ✅ Easier design preparation than manual methods
  • ✅ Systematic and consistent SDLC phases
  • ❌ Staff must be trained — resistance to change is common
  • ❌ Project size may not suit certain CASE tools
  • ❌ Quality level may not be desirable for certain applications

Q1. 32 KLOC, Organic (a=2.4, b=1.05, c=2.5, d=0.38)

COCOMO Calculation
-- Q1: 32 KLOC, Organic mode
Effort (PM)  = 2.4 × (32)^1.05
             = 2.4 × 37.88
             ≈ 90.9 Person-Months

Dev Time (T) = 2.5 × (90.9)^0.38
             = 2.5 × 9.22
             ≈ 23.05 Months

Avg Staffing = PM / T = 90.9 / 23.05 ≈ 3.94 ≈ 4 persons

Q2. 50 KLOC, Semidetached (a=3.0, b=1.12, c=2.5, d=0.35)

COCOMO Calculation
-- Q2: 50 KLOC, Semidetached mode
Effort (PM)  = 3.0 × (50)^1.12
             = 3.0 × 76.99
             ≈ 231 Person-Months

Dev Time (T) = 2.5 × (231)^0.35
             = 2.5 × 9.36
             ≈ 23.4 Months

Productivity = KLOC / PM = 50 / 231 ≈ 0.216 KLOC/PM

Q3. Project A (20 KLOC) vs Project B (60 KLOC), Organic (a=2.4, b=1.05)

COCOMO Comparison
-- Project A: 20 KLOC, Organic
PM_A = 2.4 × (20)^1.05 = 2.4 × 22.97 ≈ 55.1 PM
Productivity_A = 20 / 55.1 ≈ 0.363 KLOC/PM

-- Project B: 60 KLOC, Organic
PM_B = 2.4 × (60)^1.05 = 2.4 × 71.46 ≈ 171.5 PM
Productivity_B = 60 / 171.5 ≈ 0.350 KLOC/PM

-- Conclusion: Project A has better productivity (smaller projects are more productive)

Q1a. Importance of Feasibility Study

A feasibility study is conducted before starting the project to:

  • Determine if the project is technically achievable within existing technology
  • Assess whether the project can be completed within the allocated budget
  • Verify if the project aligns with organizational objectives
  • Identify risks early — saving time, money, and effort
  • Provide a binary Yes/No decision to prevent investment in infeasible projects
  • Ensure legal compliance and schedule adherence

Q1b. Four Aspects of Feasibility

Feasibility Type What it Checks Example
Technical Can it be developed with existing technology? Maintenance possible? Can we build a real-time chat app using available servers?
Operational Can it be operated easily? Can operations be maintained? Are there enough trained staff to operate the new ERP system?
Economic (Schedule) Can it be completed within budget? Cost-benefit positive? Does the projected ROI justify the ₹50 lakh development cost?
Schedule Can it be completed within the given deadline? Can the e-commerce platform be ready before the Diwali sale season?

Q2a. Importance of Design Phase

  • Provides the framework guiding how code should be written and personnel assigned
  • Design errors are costlier than coding errors — take more time to detect
  • Poorly designed software is unreliable, inefficient, and hard to maintain
  • Critical when systems become large and many developers are involved
  • Provides a basis for monitoring project progress

Q2b-c. Key Design Principles with Examples

Principle Definition Application Example
Modularity Divide system into smaller, manageable modules Online Shopping: Login module, Cart module, Payment module, Order module — each separate
Abstraction Focus on what a component does, not how it does it User calls "process_payment()" without knowing the internal bank API calls
Information Hiding Internal details of a module should not be exposed Payment module exposes only "pay(amount, method)" — hides encryption, bank communication
Low Coupling Modules should be as independent as possible Cart module doesn't directly access database — uses an API layer
High Cohesion Module performs a single, well-defined task seat_allotment module handles only seat selection and preferences
📝 Most Asked Exam Questions — Theory
exam▶

Unit 1: Introduction & SDLC

5 MARKS
Explain the Waterfall Model with diagram and phases.
Sequential model: Requirements → Design → Implementation → Testing → Maintenance. Each phase must complete before next begins. Best for stable requirements. Disadvantage: no working software until end, hard to accommodate changes.
5 MARKS
Compare Agile vs Plan-Driven approaches.
Agile: iterative, flexible requirements, minimal documentation, customer collaboration. Plan-driven: fixed requirements, heavy documentation, concrete plans, suitable for safety-critical systems.
5 MARKS
Explain Spiral Model with its four quadrants.
Q1: Determine Objectives; Q2: Assess & Reduce Risks; Q3: Development & Validation; Q4: Planning. Risk-driven, combines waterfall + incremental + prototyping. Best for large complex projects.

Unit 2: SRS & Design

5 MARKS
What are Functional and Non-Functional Requirements? Give examples.
Functional: What system does (features, inputs/outputs). Non-functional: How well it does it (performance, security, usability, reliability). NFRs often more critical — one failure can make entire system useless.
5 MARKS
Explain Cohesion and Coupling with types.
Cohesion: functional strength of a module (Functional > Sequential > Communicational > Procedural > Temporal > Logical). Coupling: measure of inter-module interaction (Data > Stamp > Control > Common > Content). Goal: HIGH cohesion, LOW coupling.
5 MARKS
Draw and explain UML Class Diagram with relationships.
Shows classes, attributes, methods, and relationships. Association (solid line), Aggregation (hollow diamond), Composition (filled diamond), Inheritance (hollow arrow). Visibility: + public, - private, # protected.

Unit 3: Coding

5 MARKS
What is Code Review? Differentiate Walkthrough vs Inspection.
Review checks algorithmic/logical errors (not syntax). Walkthrough: informal, coder present, uses test cases, finds if code works. Inspection: formal, coder may not be present, checks programming standards, finds specific error patterns (infinite loops, memory issues).

Unit 4: Testing & SPM

5 MARKS
Differentiate White Box and Black Box Testing.
White Box: tests internal code structure (statement coverage, branch coverage, path testing). Done by developer. Black Box: tests functionality without knowing code (equivalence partitioning, BVA). Done by test engineer.
10 MARKS
Solve COCOMO problem for given KLOC and mode.
Formula: PM = a×(KLOC)^b, Tdev = c×(PM)^d. Organic: a=2.4,b=1.05,c=2.5,d=0.38. Semidetached: a=3.0,b=1.12,c=2.5,d=0.35. Embedded: a=3.6,b=1.20,c=2.5,d=0.32. Staff = PM/Tdev, Productivity = KLOC/PM.

Unit 5: Quality & Maintenance

5 MARKS
Explain CMM Levels 1-5.
1-Initial (chaotic), 2-Repeatable (project mgmt), 3-Defined (organization standards), 4-Managed (quantitative control), 5-Optimizing (continuous improvement). Each level builds on previous.
5 MARKS
What are the four types of Software Maintenance?
Corrective (fix bugs), Adaptive (environment changes), Perfective (new features), Preventive (avoid future problems). Corrective is most common; Perfective consumes most effort.
